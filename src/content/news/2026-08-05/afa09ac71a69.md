# The Medallion Data Architecture: An Introduction
# 奖牌（Medallion）数据架构：入门指南

Data Engineering The Medallion Data Architecture: An Introduction A practical guide to Bronze, Silver and Gold, with a working Python and DuckDB example.
数据工程：奖牌数据架构入门。这是一份关于铜（Bronze）、银（Silver）和金（Gold）层的实践指南，并附带 Python 和 DuckDB 的工作示例。

ETL pipelines tend to become harder to trust as they grow in scope, and they certainly become harder to run without errors, to document, and to debug. A CSV arrives from one system, JSON comes from another, a Parquet file from somewhere else. Weeks and months go past, and before you know it, nobody is quite sure which version of the data can be trusted, which rules have been applied to it, or why an error occurred on yesterday’s dashboard.
随着 ETL 流水线规模的扩大，它们往往变得越来越难以信任，在运行不出错、文档记录和调试方面也变得更加困难。数据可能来自不同的系统：一个 CSV 文件、一个 JSON 文件，或者一个 Parquet 文件。几周甚至几个月过去后，你会发现没人能确定哪个版本的数据是可信的，哪些规则被应用到了数据上，或者为什么昨天的仪表盘会出现错误。

The medallion architecture is a practical response to that problem. It divides a data platform into three layers, usually called bronze, silver, and gold. At the boundary of each layer, there should be a clear, documented description of the data contained in that layer. This is especially true of the bronze layer, as that is where initial ingestion of your data takes place, so you’ll want to write down as much information as you can about the source of data, who or which system loads it, when it was loaded, how often it’s loaded, etc. In an ideal world, the data in each layer gets there using tools such as SQL, Python, dbt and others.
奖牌架构是解决这一问题的实用方案。它将数据平台分为三个层级，通常称为铜层、银层和金层。在每一层的边界，都应该有对该层所含数据的清晰、文档化的描述。对于铜层尤其如此，因为这是数据初始摄入的地方，因此你需要尽可能多地记录关于数据源的信息，例如谁或哪个系统加载了数据、加载时间、加载频率等。在理想情况下，每一层的数据都是通过 SQL、Python、dbt 等工具进行处理并到达该位置的。

Where did the medallion architecture come from? The bronze, silver and gold terminology was first proposed by Databricks. Databricks is a data and AI company whose cloud platform helps organisations process, manage and analyse large datasets using technologies such as Apache Spark and Delta Lake. Databricks describes the medallion structure as a multi-layered pattern in which data quality improves progressively as data moves through the three layers.
奖牌架构起源于何处？“铜、银、金”的术语最早由 Databricks 提出。Databricks 是一家数据和人工智能公司，其云平台利用 Apache Spark 和 Delta Lake 等技术，帮助组织处理、管理和分析大规模数据集。Databricks 将奖牌结构描述为一种多层模式，随着数据在三个层级中流动，数据质量会逐步提高。

Typically, the bronze level is used to store raw, unfiltered data as it arrives from the source. Records are normally immutable and append-only. Silver contains a cleaned-up version of the data in bronze. For example, null records, invalid dates, missing fields, etc., would be remedied or removed before being stored here. Gold often contains specialised, aggregate datasets defined as SQL (materialised) views derived from Silver that align with business rules. For example, data dashboards and management reports are usually built from data in the Gold layer because the data is correct, tends to be smaller, and leads to greater accuracy and lower processing times.
通常，铜层用于存储从源头到达的原始、未经过滤的数据。记录通常是不可变的，且仅支持追加。银层包含铜层数据的清理版本。例如，空记录、无效日期、缺失字段等在存储到此处之前会被修复或删除。金层通常包含专门的聚合数据集，这些数据集定义为从银层派生的 SQL（物化）视图，并符合业务规则。例如，数据仪表盘和管理报告通常基于金层的数据构建，因为这些数据准确、体量较小，且能带来更高的精确度和更短的处理时间。

Of course, systems like this have been around as long as data has. Most database engineers will have used a “staging” area to bring data into a system before farming it out to where it’s needed long before they heard the term “Medallion”. That’s a simple two-layer medallion system. Databricks just added another layer, gave it a fancy name and popularised it.
当然，这类系统与数据本身一样古老。大多数数据库工程师在听说“奖牌”这个术语之前，早就使用过“暂存（Staging）”区将数据引入系统，然后再分发到需要的地方。这就是一个简单的两层奖牌系统。Databricks 只是增加了一层，给它起了一个时髦的名字，并将其推广开来。

### What belongs in each layer? / 每一层应该包含什么？

Note that in real-life systems, the gold, silver, and bronze layers usually correspond to different schemas within a modern database or data warehouse.
请注意，在实际系统中，金、银、铜层通常对应于现代数据库或数据仓库中的不同模式（Schema）。

#### Bronze / 铜层
Bronze is a record of what arrived from the source. Useful bronze data might also include ingestion metadata alongside the source fields such as: source system and source file or event identifier, ingestion timestamp and/or business effective date, number of records ingested, batch or loading run identifier.
铜层是源头数据到达时的记录。有用的铜层数据除了源字段外，还可能包括摄入元数据，例如：源系统和源文件或事件标识符、摄入时间戳和/或业务生效日期、摄入记录数、批次或加载运行标识符。

How you deal with errors and other types of data issues at this layer stage is important. For bad and/or missing data values, these should be retained as-is and quarantined at the silver level if required. If a data load fails half-way through, because of a network failure, for example, the load should be marked as failed or superseded and re-loaded as a new batch. If additional or late data arrives, append it as another batch and record its source, ingestion time and business-effective date. If the same delivery is submitted twice, use a file hash, batch identifier or source key to prevent accidental duplication. Whatever approach is taken, ingestion should be idempotent. Processing the same source delivery more than once should not create duplicate records or otherwise change the resulting state.
在此阶段处理错误和其他类型的数据问题非常重要。对于错误和/或缺失的数据值，应按原样保留，并在必要时在银层进行隔离。如果数据加载中途失败（例如由于网络故障），则应将该加载标记为失败或被取代，并作为新批次重新加载。如果收到额外或延迟的数据，请将其作为另一个批次追加，并记录其来源、摄入时间和业务生效日期。如果同一批数据被提交了两次，请使用文件哈希、批次标识符或源键来防止意外重复。无论采取何种方法，摄入过程都应是幂等的。多次处理同一源数据不应创建重复记录或以其他方式改变最终状态。

#### Silver / 银层
Silver applies rules to the bronze layer data set that make records dependable and accurate enough to be usable. Typical transformation work includes: parsing and enforcing data types, standardising dates, currencies, country codes and units, deduplicating records, quarantining duff data, joining reference data.
银层将规则应用于铜层数据集，使记录变得可靠且准确，足以投入使用。典型的转换工作包括：解析和强制执行数据类型、标准化日期、货币、国家代码和单位、记录去重、隔离无效数据、关联参考数据。

Silver should usually retain business-level detail. It is the clean, foundational data that products and downstream systems can rely on. Getting things wrong at this level can really screw up your downstream systems and processes. For example, a silver order_total column should have a defined currency and numeric type. An order_id should have a documented uniqueness rule. If a row fails those rules, the pipeline needs an explicit outcome, e.g insertion into a quarantine table, rather than a silent omission.
银层通常应保留业务层面的细节。它是产品和下游系统可以依赖的干净的基础数据。在这一层出错会严重破坏下游系统和流程。例如，银层的 `order_total` 列应具有定义的货币和数值类型。`order_id` 应具有文档化的唯一性规则。如果某行数据违反了这些规则，流水线需要有一个明确的处理结果，例如插入到隔离表中，而不是默默地忽略。

#### Gold / 金层
Gold is organised around particular business use cases and processes. Gold typically includes: Summarised and aggregated data sets such as totals and counts by day, month, or region (e.g., total sales, active users); Star schemas or data marts built for fast queries with fewer joins; Tailored, separate data sets for specific teams like finance, marketing, or operations.
金层围绕特定的业务用例和流程进行组织。金层通常包括：汇总和聚合的数据集，例如按天、月或地区统计的总数和计数（如总销售额、活跃用户）；为快速查询而构建的、减少关联操作的星型模型或数据集市；为财务、市场或运营等特定团队定制的独立数据集。

### What tools do I need to implement a Medallion pattern? / 我需要什么工具来实现奖牌模式？
There’s no one way to do this, but as a starter, I’d say that you usually implement a medallion architecture using some kind of database, data warehouse or cloud-based object storage where your gold, silver, and bronze layers are typically different schemas in your database or folders in your object storage. This will work on anything from SQLite on your local laptop to an AWS Redshift data lake on a huge cloud-based cluster or AWS S3/Azure Blob/Google.
实现这一模式没有唯一的方法，但作为入门，通常可以使用某种数据库、数据仓库或基于云的对象存储来实现奖牌架构，其中金、银、铜层通常是数据库中的不同模式，或者是对象存储中的不同文件夹。这适用于从本地笔记本电脑上的 SQLite 到大型云集群上的 AWS Redshift 数据湖，或 AWS S3/Azure Blob/Google 等各种环境。
