# Using Agents as Tools / 使用智能体作为工具

**Agentic AI Using Agents as Tools: Building manager–specialist workflows with the OpenAI Agents SDK**
**智能体 AI：使用智能体作为工具——利用 OpenAI Agents SDK 构建“经理-专家”工作流**

When building an agent, we give it tools so that it can delegate work rather than solving everything by itself. For a well-defined operation, the tool can simply be a script-based function or an API. But once the task becomes more open-ended, it can be quite difficult to capture the problem-solving logic in a predefined script. This leads to an interesting question: Can another agent become the tool? The answer is yes. And this is the so-called “agent-as-a-tool” pattern. In this post, we’ll explore this pattern using the OpenAI Agents SDK and illustrate it with a small case study.

在构建智能体时，我们为其提供工具，以便它能够委派工作，而不是事必躬亲。对于定义明确的操作，工具可以仅仅是一个基于脚本的函数或 API。但一旦任务变得更加开放，就很难用预定义的脚本来捕捉解决问题的逻辑。这引出了一个有趣的问题：另一个智能体可以成为工具吗？答案是肯定的。这就是所谓的“智能体作为工具”（agent-as-a-tool）模式。在本文中，我们将使用 OpenAI Agents SDK 探索这种模式，并通过一个小案例进行说明。

### 1. The Agent-as-a-Tool Pattern / 1. “智能体作为工具”模式

As implied by its name, in this pattern, agents are treated as tools called by a manager agent. Commonly, this manager agent manages the overall tasks, while other agents serve as specialists. Whenever the manager needs help with a particular part of the problem, it passes that work to the relevant specialist. The specialist can then solve the delegated task using its own instructions and tools. Once it completes the task, the results are fed back to the manager, who might continue coordinating the work or produce the final response. This is one concrete pattern of a multi-agent system. It becomes useful when the boundary of a delegated task is clear, but the steps required to complete it are not. This pattern gives us a clear division of responsibility. Different specialists can be configured accordingly, but we don’t need to burden the manager agent with every implementation detail. Next, let’s build this pattern with the OpenAI Agents SDK.

顾名思义，在这种模式下，智能体被视为由“经理智能体”（manager agent）调用的工具。通常，经理智能体负责管理整体任务，而其他智能体则担任专家角色。每当经理需要处理问题的特定部分时，它就会将工作交给相关的专家。专家随后可以使用自己的指令和工具来解决委派的任务。任务完成后，结果会反馈给经理，经理可能会继续协调工作或生成最终响应。这是多智能体系统的一种具体模式。当委派任务的边界清晰，但完成任务所需的步骤不明确时，这种模式非常有用。它为我们提供了明确的职责分工。我们可以相应地配置不同的专家，而无需让经理智能体承担每一个实现细节。接下来，让我们使用 OpenAI Agents SDK 构建这种模式。

### 2. Planning a Long Layover / 2. 规划长转机行程

In this case study, we build an agentic system to help travelers plan their activities during a long layover. Think of this scenario: a family has a 10-hour layover in Munich, Germany. They would like to leave the airport, do some sightseeing, and enjoy a good meal without jeopardizing their onward flight. To create a useful itinerary, the agent needs to answer a few questions, for example: Is there enough time to leave the airport at all? What activities and food options fit the travelers? What risks should the plan consider? It’d be great if we can give the agent three purposely built tools to help answer those questions.

在本案例研究中，我们构建了一个智能体系统，帮助旅客规划长转机期间的活动。设想这样一个场景：一个家庭在德国慕尼黑有 10 小时的转机时间。他们想离开机场，进行一些观光并享用美食，同时不能影响后续航班。为了创建一个实用的行程，智能体需要回答几个问题，例如：是否有足够的时间离开机场？哪些活动和餐饮选择适合这些旅客？该计划应考虑哪些风险？如果我们能为智能体提供三个专门构建的工具来帮助回答这些问题，那就太好了。

The three tools are:
*   **logistics_tool**: checks whether the trip is feasible based on transportation and timing.
*   **local_experience_tool**: finds activities and food options.
*   **risk_tool**: identifies potential risks and suggests ways to make the plan more robust.

这三个工具分别是：
*   **logistics_tool（物流工具）**：根据交通和时间检查行程是否可行。
*   **local_experience_tool（本地体验工具）**：查找活动和餐饮选择。
*   **risk_tool（风险工具）**：识别潜在风险并建议如何使计划更稳健。

The travel planner can then call those tools and synthesize the responses into the final itinerary. But here is the problem: none of the tools can be easily implemented as a predefined function. They are all open-ended tasks, and some of the tasks, like logistics checking, even require searching current transportation information online. So, what should we do then? This is where the agent-as-a-tool pattern comes into play. Instead of using a predefined function, we use a specialist agent to act as the tool. Those specialist agents can reason about the task and use their own tools when needed. This way, we get the full flexibility of agentic problem-solving. And the best part is, from the travel planner agent’s perspective, nothing changes: it still calls a tool and receives a response. But behind that tool, however, it’s another agent that does the work.

旅行规划师随后可以调用这些工具，并将响应合成为最终行程。但问题在于：这些工具都无法轻易地实现为预定义函数。它们都是开放式任务，其中一些任务（如物流检查）甚至需要在线搜索当前的交通信息。那么我们该怎么办呢？这就是“智能体作为工具”模式发挥作用的地方。我们不使用预定义函数，而是使用专家智能体作为工具。这些专家智能体可以对任务进行推理，并在需要时使用自己的工具。通过这种方式，我们获得了智能体解决问题的全部灵活性。最棒的是，从旅行规划师智能体的角度来看，一切都没有改变：它仍然是调用一个工具并接收响应。然而，在工具的背后，是另一个智能体在执行工作。

Here comes the magic: `logistics_tool = logistics_agent.as_tool(...)`. This is how we expose this agent as the `logistics_tool`. One thing worth mentioning: the instructions we specified for `logistics_agent` is to tell the logistics agent what role to perform after it is invoked. So it is specialist agent facing. For the `tool_name` and `tool_description`, they are shown to the travel planner agent, who uses them to decide when to call this specialist. We have also set `max_turns=3`, meaning that the logistics agent can take up to three turns to complete the delegated task and return its response.

奇迹就在这里：`logistics_tool = logistics_agent.as_tool(...)`。这就是我们将该智能体公开为 `logistics_tool` 的方式。值得一提的是：我们为 `logistics_agent` 指定的指令是告诉物流智能体在被调用后执行什么角色。因此，它是面向专家智能体的。至于 `tool_name` 和 `tool_description`，它们会展示给旅行规划师智能体，后者利用这些信息决定何时调用该专家。我们还设置了 `max_turns=3`，这意味着物流智能体最多可以进行三轮交互来完成委派的任务并返回响应。
