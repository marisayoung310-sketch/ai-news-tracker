Three distinct retrieval pipelines—keyword, dense embedding, and learned sparse search—converge into ranked documents Teams building retrieval-augmented generation (RAG) systems constantly say things like “dense retrieval beats BM25” or “hybrid search works better,” and most of the time, nobody involved has actually reproduced the baseline being compared against.
三种不同的检索流水线——关键词检索、稠密向量嵌入和学习型稀疏搜索——最终都汇聚为排序后的文档。构建检索增强生成（RAG）系统的团队经常说“稠密检索优于 BM25”或“混合搜索效果更好”，但大多数情况下，相关人员并没有真正复现过他们所对比的基准模型。

BM25 is a keyword scoring method that has been used for decades and still shows up as the baseline in nearly every retrieval paper published today. Dense retrieval is now standard in production search. It uses a trained model to convert text into embeddings, then ranks documents by how closely their embeddings match the query. Learned sparse retrieval, a newer approach that sits conceptually between the two, is spreading fast.
BM25 是一种已使用数十年的关键词评分方法，至今仍出现在几乎每一篇检索相关的论文中作为基准。稠密检索现在已是生产环境搜索的标准。它利用训练好的模型将文本转换为嵌入向量，然后根据嵌入向量与查询的匹配程度对文档进行排序。学习型稀疏检索是一种较新的方法，在概念上介于两者之间，且正在迅速普及。

Many people repeat claims about BM25, dense retrieval, and SPLADE, but far fewer have run all three themselves on real benchmark data and checked whether their results match published scores. I did, on a MacBook with 16GB of memory, using a public set of exercises called the Foundations of Retrieval onboarding path, maintained by the Castorini information retrieval research group.
许多人重复着关于 BM25、稠密检索和 SPLADE 的论断，但很少有人亲自在真实的基准数据集上运行过这三种方法，并核实其结果是否与已发表的分数相符。我做到了，在一台 16GB 内存的 MacBook 上，使用了由 Castorini 信息检索研究小组维护的“检索基础（Foundations of Retrieval）”入门路径中的公开练习集。

The path uses two open-source toolkits from Castorini: Anserini, which is Java-based, and Pyserini, its Python counterpart. It tests them on two real document collections and gives exact expected scores for each exercise. Every number matched. Getting there took an out-of-memory crash, a native library crash, and a gated model access request that a valid application programming interface (API) key alone did not satisfy.
该路径使用了 Castorini 的两个开源工具包：基于 Java 的 Anserini 和其 Python 对应版本 Pyserini。它在两个真实的文档集合上对这些工具进行了测试，并为每个练习提供了精确的预期分数。所有的数字都对上了。实现这一过程经历了内存溢出崩溃、原生库崩溃，以及一个仅凭有效的 API 密钥无法满足的受限模型访问请求。

None of that shows up in the official documentation, so this article covers it as carefully as the numbers themselves. By the end, you will know how to run the three methods locally, what can break on normal hardware, and how to read the scores.
这些问题在官方文档中都没有提及，因此本文将像对待数据本身一样仔细地记录这些过程。读完本文，你将了解如何在本地运行这三种方法，在普通硬件上可能会遇到什么故障，以及如何解读评分。

The practical application is straightforward: if you are building a RAG system, a document search product, or an internal knowledge base, retrieval quality is the first thing to verify. Before changing prompts, swapping large language models, or adding agents, you need to know whether the right documents are being found at all. Reproducing these baselines gives you a reference point: what BM25 can do, what dense retrieval adds, what learned sparse retrieval costs, and how to check whether your own scoring pipeline is behaving correctly.
其实际应用非常直接：如果你正在构建 RAG 系统、文档搜索产品或内部知识库，检索质量是首要验证的目标。在更改提示词、更换大语言模型或添加智能体之前，你需要先确认是否真的找到了正确的文档。复现这些基准模型为你提供了一个参考点：BM25 能做什么，稠密检索增加了什么，学习型稀疏检索的成本是多少，以及如何检查你自己的评分流水线是否运行正常。

### What BM25, dense retrieval, and SPLADE actually do
### BM25、稠密检索和 SPLADE 到底做了什么

All three methods solve the same problem: given a search query and a large collection of documents, return the documents most likely to answer it, ranked best first. They differ only in how they turn text into something a computer can compare and rank.
这三种方法解决的是同一个问题：给定一个搜索查询和大量文档集合，返回最可能回答该查询的文档，并按相关性从高到低排序。它们的区别仅在于如何将文本转化为计算机可以比较和排序的形式。

BM25 reads a document and a query, counts which words they share, and weighs each shared word by how rare and how frequent it is. It produces a sparse vector, a long list of numbers where almost every entry is zero, and the nonzero entries are word weights. It needs no training data. The weights are determined by a fixed formula, tuned by two constants (k1 and b), rather than learned from examples.
BM25 读取文档和查询，统计它们共有的词汇，并根据这些词汇的稀有度和频率进行加权。它生成一个稀疏向量，即一个长数字列表，其中几乎所有项都为零，非零项则是词权重。它不需要训练数据。权重由固定公式决定，并通过两个常量（k1 和 b）进行调整，而不是从示例中学习得来。

Dense retrieval replaces that formula with a trained neural network. A document encoder reads the document and outputs a fixed-length list of numbers, an embedding, meant to capture meaning rather than exact wording. A query encoder does the same for the query. The two embeddings are compared with a dot product. That means multiplying matching positions and adding the results. The highest-scoring documents win. This requires a model trained on large amounts of labeled query-document pairs.
稠密检索用训练好的神经网络取代了上述公式。文档编码器读取文档并输出一个固定长度的数字列表（即嵌入向量），旨在捕捉语义而非精确措辞。查询编码器对查询执行同样的操作。这两个嵌入向量通过点积进行比较，即对应位置相乘并求和。得分最高的文档胜出。这需要使用大量标注好的“查询-文档”对进行模型训练。

Learned sparse retrieval, the category SPLADE belongs to, is a middle path. Like BM25, it produces a sparse vector where most entries are zero. Unlike BM25, a trained model determines which words matter and by how much, rather than relying on a fixed formula. SPLADE version 3 is the specific model used in this article.
学习型稀疏检索（SPLADE 所属的类别）是一种折中方案。与 BM25 一样，它生成一个大部分项为零的稀疏向量。但与 BM25 不同的是，它由训练好的模型来决定哪些词重要以及重要程度，而不是依赖固定公式。本文使用的是 SPLADE 第 3 版模型。

All three follow the same broad pattern: encode the query, encode the document, then compare the two. This is called a bi-encoder architecture. Jimmy Lin’s paper on a representational framework for information retrieval lays this out formally. Section four of this article verifies it by hand.
这三种方法都遵循相同的基本模式：编码查询、编码文档，然后进行比较。这被称为双编码器（bi-encoder）架构。Jimmy Lin 关于信息检索表示框架的论文对此进行了正式阐述。本文的第四部分将通过手动验证来证实这一点。

### Two collections, one full scale and one small on purpose
### 两个数据集：一个全规模，一个特意精简

The exercises use two test collections. MS MARCO passage ranking is a Microsoft benchmark of 8,841,823 passages with 6,980 development queries, released for non-commercial research. It is full-scale: the same core operations a production search system relies on- indexing, searching, and evaluating ranked results- run once here instead of continuously. The BM25 result here matches the official MS MARCO leaderboard entry for “BM25 (Lucene8, tuned)”, published on June 26, 2019. It is a publicly recorded benchmark result, not a number picked to make the article look good.
这些练习使用了两个测试集。MS MARCO 段落排序数据集是微软的一个基准，包含 8,841,823 个段落和 6,980 个开发查询，供非商业研究使用。它是全规模的：生产环境搜索系统所依赖的核心操作（索引、搜索和评估排序结果）在这里运行了一次，而不是持续运行。此处的 BM25 结果与 2019 年 6 月 26 日发布的官方 MS MARCO 排行榜上的“BM25 (Lucene8, tuned)”条目相符。这是一个公开记录的基准结果，并非为了让文章好看而挑选的数字。

NFCorpus is a smaller medical retrieval dataset with 3,633 documents and 3,237 queries. Because it is small, all three methods can run on a laptop CPU in minutes or hours instead of requiring a GPU. It is used here for a direct, same collection comparison of BM25, dense retrieval, and SPLADE side by side. Treat the NFCorpus numbers as a real result on this specific dataset, not a general ranking of which method wins everywhere. Its small size is what makes the comparison practical on a laptop, not a shortcut around real evaluation.
NFCorpus 是一个较小的医学检索数据集，包含 3,633 个文档和 3,237 个查询。由于规模较小，这三种方法都可以在笔记本电脑的 CPU 上运行，耗时仅需几分钟到几小时，无需 GPU。此处将其用于 BM25、稠密检索和 SPLADE 在同一数据集上的直接对比。请将 NFCorpus 的数据视为该特定数据集上的真实结果，而非某种方法在任何地方都胜出的通用排名。其小规模正是使得在笔记本电脑上进行对比变得可行，而不是逃避真实评估的捷径。
