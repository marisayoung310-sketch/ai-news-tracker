# How to Debug AI Coding Agents When They Change the Wrong Thing
# 如何调试修改了错误内容的 AI 编程智能体

A practical tutorial for recording model tool requests, real function results, patches, checks, screenshots, and a saved run log.
这是一份关于记录模型工具请求、真实函数结果、补丁、检查、截图以及保存运行日志的实用教程。

***

When you give a coding agent a request, the hard part is not always writing code. The hard part is showing that the agent understood the request, changed the right place, and verified the right result. An agent can do several things during a run and still end with a short answer like “fixed.” That answer hides the important details: what it inspected, what it changed, what it ran, and what proved the fix worked.
当你向编程智能体（Coding Agent）发出请求时，难点往往不在于编写代码，而在于证明智能体确实理解了请求、修改了正确的位置，并验证了正确的结果。智能体在运行过程中可能会执行多项操作，最后却只给出一个简短的回答，比如“已修复”。这个回答掩盖了关键细节：它检查了什么、修改了什么、运行了什么，以及是什么证据证明修复生效了。

Without evidence, you cannot tell whether the final check matched the user’s original complaint. That gap shows up in ordinary coding requests. A passing build can show the app still compiles, even though the button is still broken. A passing test can mean the assertion got weaker. A plausible route change can still miss the handler that serves the response. A coding agent should change code and prove what it inspected, what it changed, what it ran, and what result made the fix acceptable.
如果没有证据，你无法判断最终的检查是否对应了用户最初的反馈。这种脱节在日常编程请求中很常见。构建通过可能只是说明应用仍能编译，但按钮可能依然是坏的；测试通过可能意味着断言被削弱了；看似合理的路由修改可能遗漏了处理响应的处理器。编程智能体不仅应该修改代码，还应证明它检查了什么、修改了什么、运行了什么，以及什么结果使得修复方案是可接受的。

Software engineering already has a name for part of this problem: traceability. Torkar et al. describe requirements traceability as the ability to follow a requirement from its emergence to its fulfillment. In coding agent work, the same idea becomes more immediate: can you connect the user’s request to the files inspected, the patch applied, the command result, and the final verification check?
软件工程中已经有一个术语来描述这个问题的一部分：可追溯性（Traceability）。Torkar 等人将需求可追溯性描述为：能够追踪一个需求从产生到实现的全过程。在编程智能体的工作中，这一概念变得更加直接：你能否将用户的请求与所检查的文件、应用的补丁、命令结果以及最终的验证检查关联起来？

Model Context Protocol (MCP) describes a standard way for artificial intelligence applications to connect to files, tools, data sources, and other external systems. That standard only helps if the tool run leaves evidence a developer can review. The tutorial tackles a problem both developers and vibe coders run into: the agent changes something, sounds confident, and leaves you guessing whether it touched the right part of the app.
模型上下文协议（MCP）描述了一种人工智能应用连接文件、工具、数据源和其他外部系统的标准方式。但只有当工具运行留下了开发者可以审查的证据时，该标准才真正有用。本教程旨在解决开发者和“直觉编程者”（vibe coders）都会遇到的问题：智能体修改了某些内容，表现得信心十足，却让你怀疑它是否触及了应用中正确的部分。

The example uses a user interface bug because visual fixes are easy to get wrong and easy to verify in a browser. A pricing card has a primary button that overflows on a mobile screen size. The repair is a targeted Cascading Style Sheets (CSS) change. The useful part is the saved evidence around the repair: file reads, a wrong selector attempt caught by the browser check, a targeted patch, build output, Document Object Model (DOM) measurements, and before and after screenshots.
本示例使用了一个用户界面 Bug，因为视觉修复很容易出错，同时也容易在浏览器中验证。一个定价卡片的主按钮在移动端屏幕尺寸下会溢出。修复方案是对层叠样式表（CSS）进行针对性修改。最有价值的部分是围绕修复过程保存的证据：文件读取记录、被浏览器检查捕获的错误选择器尝试、针对性的补丁、构建输出、文档对象模型（DOM）测量数据，以及修复前后的截图。

By the end, you should have a review pattern you can adapt to common coding-agent failures: the wrong file, the wrong selector, the wrong function, a skipped command, an edited test, a broken route, a missed edge case, or a fix that passes one check but fails the user’s actual request.
读完本文，你将掌握一种审查模式，可以应用于常见的编程智能体故障：修改了错误的文件、错误的选择器、错误的函数，跳过了命令，修改了测试，破坏了路由，遗漏了边界情况，或者修复方案通过了某项检查但未能满足用户的实际需求。

***

### The developer problem is broader than UI
### 开发者面临的问题远不止 UI

Here is the kind of request many developers now give to Codex, Claude Code, Cursor, or another coding agent: “Fix the button in the pricing card. It overflows on mobile.” That prompt sounds clear to a human. It is not enough evidence for an agent.
以下是许多开发者现在向 Codex、Claude Code、Cursor 或其他编程智能体发出的典型请求：“修复定价卡片中的按钮。它在移动端溢出了。”这对人类来说很清晰，但对智能体而言，证据还不够。

The same review problem appears outside user interface work:
同样的审查问题也出现在用户界面工作之外：

*   **“Fix the checkout bug” can change the wrong payment branch.** The agent might edit the PayPal flow when the bug is actually in the Stripe flow, or patch guest checkout when the failure is in logged in checkout.
    **“修复结账 Bug”可能会修改错误的支付分支。** 当 Bug 实际上在 Stripe 流程中时，智能体可能会编辑 PayPal 流程；或者当故障发生在已登录结账时，它却去修补了访客结账。
*   **“Make this test pass” can weaken the assertion instead of fixing the behavior.** Instead of fixing the broken code, the agent might change the test so it checks less. The test passes, but the real bug remains.
    **“让这个测试通过”可能会削弱断言，而不是修复行为。** 智能体可能不会去修复损坏的代码，而是修改测试以减少检查项。测试通过了，但真正的 Bug 依然存在。
*   **“Update the API response” can edit a type but miss the handler.** The agent might update a TypeScript type or schema, but forget to change the backend function that actually returns the response.
    **“更新 API 响应”可能会编辑类型却遗漏了处理器。** 智能体可能更新了 TypeScript 类型或模式，却忘记修改实际返回响应的后端函数。
*   **“Fix auth redirect” can patch the frontend while the backend still returns the wrong status.** The agent might change React routing, but the real issue is the server returning 401 instead of 302, or missing a session cookie.
    **“修复身份验证重定向”可能会修补前端，而后端仍返回错误的状态码。** 智能体可能修改了 React 路由，但真正的问题是服务器返回了 401 而不是 302，或者丢失了会话 Cookie。
*   **“Clean up this function” can change behavior while looking like a refactor.** A refactor should preserve behavior. The agent might rename, reorder, or simplify code in a way that changes what the function does.
    **“清理这个函数”可能会在看起来像重构的同时改变行为。** 重构应该保持行为不变。智能体可能会以改变函数功能的方式重命名、重新排序或简化代码。

The question is the same in each case: what did the model ask to do, what code actually changed, and what check proved the user’s complaint was fixed?
在每种情况下，问题都是一样的：模型被要求做什么，代码实际上发生了什么变化，以及什么检查证明了用户的投诉已得到解决？

The agent still has to answer several questions: Which file owns the pricing card? Which selector is the target? Is the problem caused by the card, the grid, or the button? What does “mobile” mean for this check? Did the rendered UI change, or did only the code change?
智能体仍然需要回答几个问题：哪个文件拥有定价卡片？哪个选择器是目标？问题是由卡片、网格还是按钮引起的？对于这次检查，“移动端”意味着什么？渲染后的 UI 发生了变化，还是仅仅代码发生了变化？
