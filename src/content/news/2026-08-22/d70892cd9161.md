# Running Codex as a Headless Agent
# 将 Codex 作为无头代理运行

**Agentic AI: Running Codex as a Headless Agent**
**代理式 AI：将 Codex 作为无头代理运行**

**Turning Codex from an interactive assistant into a programmable automation component**
**将 Codex 从交互式助手转变为可编程的自动化组件**

Most of us use Codex interactively in a terminal or an IDE. This is useful. But it also leads to a natural question: Can Codex become a callable part of our own workflow? Let’s answer that in this post. Specifically, we’ll explore how to run Codex as a headless agent inside a small automation workflow, and illustrate the idea with a concrete case study.
我们大多数人都在终端或 IDE 中以交互方式使用 Codex。这很有用，但也引出了一个自然而然的问题：Codex 能否成为我们工作流中可调用的一个环节？本文将回答这个问题。具体来说，我们将探讨如何在小型自动化工作流中将 Codex 作为无头（headless）代理运行，并通过一个具体的案例研究来说明这一构想。

### 1. The Workflow Shape We Want
### 1. 我们想要的工作流形态

We can think of Codex as a very capable agent. When we use Codex interactively, it lives inside a conversation. You need to be there the whole time to review and steer it toward what you actually want. A headless workflow doesn’t require that. There, Codex stops being a conversation partner and becomes just one callable step in a larger process. At a high level, we can think of the workflow like this:
我们可以将 Codex 视为一个能力极强的代理。当我们以交互方式使用它时，它存在于对话之中。你需要全程在场进行审查，并引导它完成你真正想要的任务。而无头工作流则不需要这样。在这种模式下，Codex 不再是对话伙伴，而仅仅是更大流程中一个可调用的步骤。从宏观上看，我们可以这样构思工作流：

*Figure 1. Codex in headless mode: the workflow prepares a clear task for Codex, and Codex returns an output that the next step can consume.*
*图 1. 无头模式下的 Codex：工作流为 Codex 准备明确的任务，Codex 返回可供下一步处理的输出。*

The trick is keeping that step bounded: the workflow supplies the task context for Codex, and Codex returns an output that the next step can easily consume. This pattern is useful when the overall process is repeatable, but one step requires agentic work. For example, a scheduled job may need to prepare a weekly research digest, or a CI workflow may need to run an automated review. By bringing Codex into a larger workflow, we get the benefits of both sides: ordinary code keeps the process deterministic, structured, and easy to inspect, while Codex handles the open-ended parts that can genuinely benefit from an agent. This is the workflow shape we will build in the case study.
关键在于保持该步骤的边界清晰：工作流为 Codex 提供任务上下文，Codex 返回可供后续步骤轻松消费的输出。当整体流程可重复，但其中某一步骤需要代理式工作时，这种模式非常有用。例如，定时任务可能需要准备每周的研究摘要，或者 CI 工作流可能需要运行自动化审查。通过将 Codex 引入更大的工作流，我们兼具了两者的优势：普通代码保持了流程的确定性、结构化和易于检查，而 Codex 则处理那些真正能从代理能力中受益的开放式任务。这就是我们将在案例研究中构建的工作流形态。

### 2. Case Study: Building a Research Digest Workflow
### 2. 案例研究：构建研究摘要工作流

Here, we build a small automation workflow that asks Codex to research recent developments on a topic and turns the result into an HTML digest. In code, our workflow looks like this in Python:
在这里，我们将构建一个小型的自动化工作流，要求 Codex 研究某个主题的最新进展，并将结果转化为 HTML 摘要。在 Python 代码中，我们的工作流如下所示：

```python
run = prepare_research_task()
brief = run_codex(run)
html_path = render_digest(brief)
```

The division of labor is very simple. Python prepares the task and produces the final artifact. The open-ended research step in the middle is handled by Codex. Now let’s unpack the workflow one piece at a time.
分工非常简单：Python 负责准备任务并生成最终产物，而中间的开放式研究步骤则由 Codex 处理。现在让我们逐一拆解这个工作流。

#### 2.1 Preparing the Run
#### 2.1 准备运行

In the first step, we only prepare the inputs needed for the Codex run. This means three things: the prompt, the output schema, and the file locations for the final summary and execution trace. Just like configuring a usual agent, we need to prepare a prompt for Codex to clarify the task and our expected outcome. We start with the prompt. Just like configuring a usual agent, we need to tell Codex what the task is and what our expected outcome is. We use the following prompt template:
在第一步中，我们仅准备 Codex 运行所需的输入。这包括三项内容：提示词（prompt）、输出模式（schema）以及最终摘要和执行追踪的文件路径。就像配置普通代理一样，我们需要为 Codex 准备提示词，以明确任务和预期结果。我们从提示词开始，告诉 Codex 任务是什么以及我们期望的结果。我们使用以下提示词模板：

> Research material developments in {{TOPIC}} from {{WINDOW_START}} through {{WINDOW_END}}, inclusive, using live web search. Return at most {{MAX_EVENTS}} events. For each event, include:
> - date
> - title
> - category
> - summary
> - why it matters
> - sources
> Return only the JSON object described by the supplied schema.
> 使用实时网络搜索，研究 {{TOPIC}} 在 {{WINDOW_START}} 到 {{WINDOW_END}}（含）期间的重大进展。最多返回 {{MAX_EVENTS}} 个事件。对于每个事件，请包含：
> - 日期
> - 标题
> - 类别
> - 摘要
> - 重要性说明
> - 来源
> 仅返回所提供模式中描述的 JSON 对象。

Then Python turns this into a concrete prompt for one run:
然后，Python 将其转化为单次运行的具体提示词：

```python
from datetime import date, timedelta

def prepare_research_task(
    topic: str,
    as_of: date,
    lookback_days: int,
    max_events: int,
) -> dict:
    window_end = as_of
    window_start = as_of - timedelta(days=lookback_days - 1)
    prompt = (
        PROMPT_TEMPLATE
        .replace("{{TOPIC}}", topic)
        .replace("{{WINDOW_START}}", window_start.isoformat())
        .replace("{{WINDOW_END}}", window_end.isoformat())
        .replace("{{MAX_EVENTS}}", str(max_events))
    )
    return {
        "prompt": prompt,
        "schema_file": "schemas/evidence_brief.schema.json",
        "brief_file": "outputs/brief.json",
        "trace_file": "outputs/run.jsonl",
    }
```

Note that instead of asking Codex to return a free-form report, we ask it to return a structured JSON. This is important because the next step can consume Codex’s result programmatically. Here is the schema we use:
请注意，我们没有要求 Codex 返回自由格式的报告，而是要求它返回结构化的 JSON。这一点很重要，因为下一步可以以编程方式消费 Codex 的结果。以下是我们使用的模式：

```json
{
  "topic": "...",
  "window_start": "YYYY-MM-DD",
  "window_end": "YYYY-MM-DD",
  "summary": "...",
  "events": [
    {
      "date": "YYYY-MM-DD",
      "title": "...",
      "category": "...",
      "summary": "...",
      "why_it_matters": "...",
      "sources": [
        {
          "publisher": "...",
          "title": "...",
          "published_date": "YYYY-MM-DD",
          "url": "https://..."
        }
      ]
    }
  ]
}
```

Also, we use `brief_file` to store the final structured answer, and `trace_file` to store the execution trace from the headless run. Those paths will be used when we call Codex in the next step. At this point, nothing agentic has happened yet. We only did the necessary preparation work.
此外，我们使用 `brief_file` 存储最终的结构化答案，并使用 `trace_file` 存储无头运行的执行追踪。这些路径将在下一步调用 Codex 时使用。此时，尚未发生任何代理行为，我们仅完成了必要的准备工作。

#### 2.2 Running Codex Headlessly
#### 2.2 无头运行 Codex

First things first, make sure the Codex CLI is available from the command line. If you already have Node.js and npm installed, you can do this:
首先，确保命令行可以使用 Codex CLI。如果你已经安装了 Node.js 和 npm，可以执行以下操作：

```bash
npm install --global @openai/codex
```

Then sign in and check the installation:
然后登录并检查安装情况：

```bash
codex login
codex login status
codex --version
```

To run Codex non-interactively, we need `codex exec`. The core command looks like this:
要以非交互方式运行 Codex，我们需要使用 `codex exec`。核心命令如下所示：

```bash
codex --search exec \
  --model gpt-5.6-sol \
  --json \
  --output-schema schemas/evidence_brief.schema.json \
  -o outputs/brief.json \
  -
```

Some explanations on the arguments:
关于参数的一些说明：
* `--search`: allows Codex to use live web search.
* `--search`: 允许 Codex 使用实时网络搜索。
* `--model`: which model to use for the run.
* `--model`: 运行所使用的模型。
* `--output-schema`: tells Codex the expected output shape.
* `--output-schema`: 告知 Codex 预期的输出格式。
* `-o`: tells Codex to write the final answer to `brief.json`.
* `-o`: 告知 Codex 将最终答案写入 `brief.json`。
* `--json`: makes Codex emit JSONL events to stdout, which we write to `run.jsonl` (the trace file).
* `--json`: 使 Codex 将 JSONL 事件输出到标准输出（stdout），我们将其写入 `run.jsonl`（追踪文件）。
* `-`: tells Codex to read the prompt from stdin.
* `-`: 告知 Codex 从标准输入（stdin）读取提示词。

Codex CLI also supports execution controls that are useful in automated environments. For example, we have the `--sandbox` argument, such as `--sandbox read-only` (limits the run to read-only access) and `--sandbox workspace-write` (allows changes inside the workspace).
