# The Generated Helper Passed Locally, Then Died in a Clean Container Because It Read a Global I Never Passed

# 生成的辅助函数在本地运行通过，却在干净的容器中崩溃，原因竟是它读取了一个我从未传递的全局变量

I almost shipped a small feature-flag helper that worked on my laptop and crashed in the clean Docker image. The generated source looked self-contained, and my local smoke test gave the exact boolean I expected, so I assumed the problem was the deployment environment. It was not. The generated function was silently reading module-level variables that my interactive shell still had from an older script. The clean container did not have those globals, so the same code raised `NameError` at the first call. I rebuilt the failure in a tiny harness and then added a pre-execution check that catches this class of problem before the code leaves the test directory.

我差点发布了一个小的功能标志（feature-flag）辅助函数，它在我的笔记本电脑上运行正常，但在干净的 Docker 镜像中却崩溃了。生成的源代码看起来是自包含的，且我的本地冒烟测试给出了我预期的布尔值，所以我以为问题出在部署环境上。事实并非如此。生成的函数在静默地读取模块级变量，而这些变量是我之前的脚本留在交互式 Shell 中的。干净的容器中没有这些全局变量，因此相同的代码在第一次调用时就抛出了 `NameError`。我在一个小型的测试工具中重现了该故障，并添加了一个执行前检查，以便在代码离开测试目录之前捕获此类问题。

### The generated code looked self-contained
### 生成的代码看起来是自包含的

The helper was supposed to tell me whether a feature flag was enabled for a given name. The generated source was short enough to trust:
```python
generated_source = '''
def is_enabled(feature):
    if DEBUG:
        return feature in FEATURE_STORE
    return feature in DEFAULT_FEATURES
'''
```
The function has three names it expects to find somewhere else: `DEBUG`, `FEATURE_STORE`, and `DEFAULT_FEATURES`. None of them is a parameter, a return value, or an import. They are free globals, but the source does not say that, and a quick glance at the function body can miss it.

### Why my laptop passed while the container failed
### 为什么我的笔记本电脑通过了测试，而容器却失败了

My local Python session still had the leftovers from a previous experiment. I executed the generated snippet in a namespace that happened to contain exactly the names it needed, so every branch ran without incident:
```python
globals_here = {
    'DEBUG': False,
    'FEATURE_STORE': {'dark': False},
    'DEFAULT_FEATURES': {'dark', 'beta'},
}
exec(generated_source, globals_here)
print(globals_here['is_enabled']('dark'))
```
That printed `False`, which matched my expectation. The same code, however, behaved very differently in an empty namespace that simulated a clean container:
```python
clean_ns = {}
exec(generated_source, clean_ns)
try:
    print(clean_ns['is_enabled']('dark'))
except NameError as exc:
    print(f"clean execution failed: {exc}")
```
The output made the hidden dependency visible:
```

clean execution failed: name 'DEBUG' is not defined
```
Only the second run told the truth. The first run passed because my environment had already provided the missing pieces, not because the generated code was complete.

### Reproduce the silent global capture
### 重现静默的全局变量捕获

I first captured this bug while generating a small helper with MonkeyCode's free model access, then I re-ran the clean-namespace check using its free server option so the reproduction would not depend on whatever globals happened to be in my shell.

Disclosure: This article was prepared as part of MonkeyCode's product outreach. The problem is provider-neutral, so the fix belongs in the code path that turns model output into an artifact for evaluation. A model can produce clean syntax and still create a function that depends on state the caller never declared. The most useful check is to find every name the generated code loads but neither assigns nor receives as a parameter. I use an AST walk for that, because a regex that scans for identifiers is too easy to fool with nested functions, comprehensions, and string annotations.

我最初是在使用 MonkeyCode 的免费模型访问权限生成一个小辅助函数时捕获到这个 Bug 的，随后我使用其免费服务器选项重新运行了干净命名空间检查，以确保重现过程不依赖于我 Shell 中恰好存在的任何全局变量。

披露：本文是 MonkeyCode 产品推广的一部分。这个问题与提供商无关，因此修复方案应位于将模型输出转换为评估工件的代码路径中。模型可以生成语法正确的代码，但仍然可能创建依赖于调用者从未声明的状态的函数。最有用的检查方法是找出生成代码加载的所有名称，且这些名称既未被赋值也未作为参数接收。我为此使用了 AST（抽象语法树）遍历，因为扫描标识符的正则表达式很容易被嵌套函数、推导式和字符串注解所误导。

### Find free globals before execution
### 在执行前查找自由全局变量

This small analyzer collects locally bound names, then subtracts them from all loaded names:
```python
import ast, builtins

def free_globals(source):
    tree = ast.parse(source)
    local_names = set(dir(builtins))
    for node in ast.walk(tree):
        if isinstance(node, ast.Name) and isinstance(node.ctx, ast.Store):
            local_names.add(node.id)
        elif isinstance(node, ast.arg):
            local_names.add(node.arg)
        elif isinstance(node, (ast.FunctionDef, ast.ClassDef)):
            local_names.add(node.name)
        elif isinstance(node, ast.Import):
            for alias in node.names:
                local_names.add(alias.asname or alias.name.split('.')[0])
        elif isinstance(node, ast.ImportFrom):
            for alias in node.names:
                local_names.add(alias.asname or alias.name)
    
    referenced = set()
    for node in ast.walk(tree):
        if isinstance(node, ast.Name) and isinstance(node.ctx, ast.Load):
            referenced.add(node.id)
            
    return sorted(referenced - local_names)

print(free_globals(generated_source))
```
Running that script prints: `['DEFAULT_FEATURES', 'DEBUG', 'FEATURE_STORE']`. The list is the missing contract. Whenever `free_globals` returns a non-empty list, the generated artifact is not self-contained and should not be treated as a finished unit until the caller either passes those names explicitly or marks them as an intentional runtime dependency.

这个小型分析器会收集局部绑定的名称，然后从所有加载的名称中减去它们：

运行该脚本会打印：`['DEFAULT_FEATURES', 'DEBUG', 'FEATURE_STORE']`。这个列表就是缺失的契约。每当 `free_globals` 返回非空列表时，生成的工件就不是自包含的，在调用者显式传递这些名称或将其标记为有意为之的运行时依赖项之前，不应将其视为完成的单元。

### Run generated code with an empty namespace
### 在空命名空间中运行生成的代码

The analyzer tells you what is missing, but it does not prove the function works. A second guard is to execute the generated source in a namespace that contains only builtins and the values you deliberately inject. That is roughly what the earlier `clean_ns` block did, and it is cheap enough to run before every merge. I keep these two checks in separate stages because they catch different mistakes:

1. **Static check**: walk the AST and fail fast when free globals exist.
2. **Runtime check**: execute with an empty namespace and assert that the result matches a few expected values.

If the generated function expects a global by design, I pass it through an allowlist instead of letting the local shell supply it accidentally. That way the environment is as deliberate as the generated code itself.

分析器告诉你缺少什么，但它不能证明函数能正常工作。第二道防线是在仅包含内置函数和你刻意注入的值的命名空间中执行生成的源代码。这大致就是前面 `clean_ns` 代码块所做的，而且在每次合并前运行它的成本很低。我将这两个检查放在不同的阶段，因为它们捕获的是不同的错误：

1. **静态检查**：遍历 AST，当存在自由全局变量时立即失败。
2. **运行时检查**：在空命名空间中执行，并断言结果符合几个预期值。

如果生成的函数设计上就需要全局变量，我会通过白名单传递它，而不是让本地 Shell 意外地提供它。这样，环境就和生成的代码本身一样是经过深思熟虑的。

### When a missing global is a real feature
### 当缺失的全局变量是真正的功能时

Not every free variable is a bug. A generated data-analysis function may be allowed to rely on `pandas` or `numpy` as an injected dependency, and a generated SQL helper may be allowed to read a connection object from an application context. The rule I follow is not to ban globals outright. It is to make them visible:

* Add the name to an explicit allowlist before execution.
* Pass the dependency through a parameter or a documented context object when possible.
* Never let a local shell or a previous script provide the missing name by accident.
* Fail the evaluation if a free global appears outside the allowlist.

That distinction is what prevents a function from being portable on my laptop and broken elsewhere.

并非每个自由变量都是 Bug。生成的某些数据分析函数可能被允许依赖 `pandas` 或 `numpy` 作为注入的依赖项，生成的 SQL 辅助函数也可能被允许从应用程序上下文中读取连接对象。我遵循的原则不是完全禁止全局变量，而是让它们可见：

* 在执行前将名称添加到显式白名单中。
* 尽可能通过参数或文档化的上下文对象传递依赖项。
* 绝不让本地 Shell 或之前的脚本意外地提供缺失的名称。
* 如果在白名单之外出现自由全局变量，则评估失败。

这种区分正是防止函数在我的笔记本电脑上可移植而在其他地方崩溃的关键。
