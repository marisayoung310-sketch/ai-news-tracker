# Webwright: Why AI Web Agents Should Write Code, Not Click
# Webwright：为什么 AI 网络代理应该编写代码，而不是点击鼠标

For years, web agents have worked one click at a time—and often fallen apart on long tasks. Microsoft Research’s Webwright makes a different bet: give the model a terminal and let it write the program instead. On long-horizon tasks, the same GPT-5.4 model jumps from 33.5% to 60.1% success. And instead of leaving behind a click trace, it leaves something you can actually use again: a command-line tool.
多年来，网络代理（Web agents）一直以“一次点击”的方式工作，且在处理长任务时往往会失败。微软研究院（Microsoft Research）的 Webwright 押注于另一种方案：为模型提供一个终端，让它直接编写程序。在长周期任务中，同一款 GPT-5.4 模型的成功率从 33.5% 跃升至 60.1%。而且，它留下的不再仅仅是一串点击记录，而是一个你可以重复使用的工具：命令行脚本。

### 1. Introduction: the web won’t hold still
### 1. 引言：变幻莫测的网络

If you have built a web agent recently, you know the failure pattern. You give it a task like “pull every listing from this directory into a spreadsheet” and watch it inch forward. It reads the page. It predicts a click. It waits for the new DOM, the page structure the browser sees. It reads again, predicts again, waits again.
如果你最近开发过网络代理，你一定熟悉这种失败模式。你给它一个任务，比如“将此目录中的所有列表提取到电子表格中”，然后看着它缓慢推进。它读取页面，预测点击位置，等待新的 DOM（浏览器所见的页面结构），然后再次读取、再次预测、再次等待。

Then, somewhere around step 40, things fall apart. A modal pops up unexpectedly. The “next page” button moves. The agent mistakes one element for another. Any one of these can derail the whole task. The deeper problem isn’t the bad click. It’s how the agent operates: look at the page, decide on one action, see what changed, then decide again. It repeats this loop over and over, without a durable plan for how to complete the task from start to finish.
然后，大约在第 40 步左右，事情就会崩溃。一个模态框意外弹出，“下一页”按钮位置变了，或者代理把一个元素误认为是另一个。任何一个小问题都可能导致整个任务脱轨。更深层的问题不在于那次错误的点击，而在于代理的运作方式：观察页面、决定一个动作、观察变化、再次决定。它不断重复这个循环，却没有一个从头到尾完成任务的持久计划。

The field has tried a few different ways to make this loop more reliable. Some agents, like OpenAI’s Operator and Anthropic’s Computer Use, work from screenshots and interact with a website much like a person would. Others, like WebVoyager, use the page’s DOM to understand what elements are available and decide which one to interact with. Benchmarks such as Mind2Web and WebArena made these systems easier to compare by giving agents a standard set of actions—click, type, scroll, select. And open-source tools like browser-use, Skyvern, Stagehand, and LaVague have packaged these ideas into APIs that engineers can more easily build into real applications.
业界已经尝试了几种方法来提高这个循环的可靠性。一些代理（如 OpenAI 的 Operator 和 Anthropic 的 Computer Use）通过截图工作，像人类一样与网站交互。另一些（如 WebVoyager）则利用页面的 DOM 来理解可用元素并决定交互对象。Mind2Web 和 WebArena 等基准测试通过为代理提供标准动作集（点击、输入、滚动、选择）使这些系统更易于比较。而 browser-use、Skyvern、Stagehand 和 LaVague 等开源工具则将这些理念封装成 API，方便工程师构建实际应用。

These approaches make the loop more reliable, but they don’t change how it fundamentally works: the agent still takes one action at a time, waits to see what happens, then decides what to do next. And when the task is over, it hasn’t built anything reusable—it has only completed a sequence of clicks.
这些方法确实提高了循环的可靠性，但并没有改变其根本运作方式：代理仍然是一次执行一个动作，等待结果，然后再决定下一步。当任务结束时，它没有构建任何可重用的东西，仅仅是完成了一系列点击操作。

Webwright, a browser-agent framework from Microsoft Research and the University of Hong Kong, takes a different approach. Its tagline captures the idea: “A terminal is all you need for web agents.” Instead of asking the model to figure out the next click, Webwright has agents writing and running code—using bash and Playwright scripts to open browsers, inspect pages, and carry out the task. The result isn’t just a long sequence of browser actions. It’s a program engineers can inspect, rerun, modify, and reuse.
Webwright 是由微软研究院和香港大学开发的一个浏览器代理框架，它采取了不同的路径。其口号概括了这一理念：“终端就是网络代理所需的一切。” Webwright 不再要求模型去推测下一次点击，而是让代理编写并运行代码——使用 bash 和 Playwright 脚本来打开浏览器、检查页面并执行任务。最终产出的不仅仅是一长串浏览器操作，而是一个工程师可以检查、重运行、修改和复用的程序。

### 2. Why web agents keep breaking
### 2. 为什么网络代理总是崩溃

The shift to “write code” matters because it addresses the underlying problem, not just the symptoms. Today’s web agents differ in how they understand a page—some look at screenshots, others read the DOM—but most still work the same way: take one browser action, see what happens, then decide on the next one. That works for short tasks. But the longer the task runs, the more chances there are for one bad click, a changed page, or a misread element to throw everything off.
转向“编写代码”至关重要，因为它解决了根本问题，而不仅仅是症状。当今的网络代理在理解页面的方式上各不相同——有的看截图，有的读 DOM——但大多数的工作方式依然相同：执行一个浏览器动作，观察结果，再决定下一个动作。这在短任务中有效，但任务运行时间越长，出现错误点击、页面变动或元素识别错误导致全盘崩溃的几率就越高。
