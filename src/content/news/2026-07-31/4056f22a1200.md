# How to Build a Context Layer and a Company Brain
# 如何构建上下文层与企业大脑

What it actually takes to turn a company's scattered knowledge into something an LLM can reliably use — and why the demo is 5% of the work.
将一家公司零散的知识转化为大语言模型（LLM）能够可靠使用的资源，究竟需要做些什么？为什么演示原型（Demo）只占整个工作的 5%？

Every company that adopts LLMs arrives at the same idea: “What if the model knew everything we know?” The warehouse schemas, the Notion pages, the Slack threads where decisions actually get made, the tribal knowledge about which table is deprecated and which column lies. A company brain.
每家采用大语言模型的公司都会产生同一个想法：“如果模型能知道我们所知道的一切会怎样？”无论是数据仓库的架构、Notion 页面、做出决策的 Slack 讨论串，还是关于哪些表已弃用、哪些列存在误导的“部落知识”。这就是企业大脑。

The demo version is a weekend project: chunk documents, embed them, retrieve top-k on cosine similarity, paste into a prompt. It works impressively well on the first ten questions — then falls apart in production, quietly. This article is about the gap, based on a production system doing this across dozens of sources for many tenants.
演示版本只是一个周末项目：对文档进行分块、向量化、通过余弦相似度检索前 K 个结果，然后粘贴到提示词中。它在前十个问题上表现惊人，但在生产环境中却会悄无声息地崩溃。本文将基于一个在多个租户、数十个数据源上运行的生产系统，探讨这其中的差距。

### What a context layer actually is
### 什么是真正的上下文层

Not a vector database. A vector database is one index inside it. It’s a system that continuously maps source systems into normalized, typed context items; indexes them in multiple specialized ways; composes the right subset into a token budget at query time; learns from curation and usage; and acts on the sources it describes — all with tenancy, permissions, freshness, and cost as first-class constraints.
它不是向量数据库。向量数据库只是其中的一个索引。它是一个能够持续将源系统映射为标准化、类型化上下文条目的系统；它以多种专业方式对这些条目进行索引；在查询时将正确的子集组合到 Token 预算内；从策展和使用中学习；并对其所描述的源系统采取行动——所有这些都将租户隔离、权限、时效性和成本作为核心约束。

Each verb hides a hard distributed-systems problem the demo never meets, because the demo ingests once, has one user, and is never asked “why didn’t it know about X?”
每一个动词背后都隐藏着演示原型从未遇到过的复杂分布式系统问题，因为演示原型通常只摄取一次数据、只有一个用户，且从不会被问到“为什么它不知道 X？”

### Part 1: Continuous mapping
### 第一部分：持续映射

Ingestion is not a batch job; it’s a reconciliation loop that never terminates. Tables get dropped, channels archived, pages edited, permissions revoked. A brain that’s a week stale is worse than useless, because people trust it.
数据摄取不是批处理作业，而是一个永不终止的协调循环。表会被删除、频道会被归档、页面会被编辑、权限会被撤销。一个滞后一周的大脑比毫无用处更糟糕，因为人们会信任它。

An ontology, not a pile of connectors. One sync script per source means twenty implementations of “list, fetch, paginate, handle deletes,” each with its own bugs. Instead, describe each source declaratively as a datamap — a typed hierarchy of what exists there. A warehouse is connection → database → schema → table → column, with context types hanging off each level; a wiki is space → page → block.
要建立本体（Ontology），而不是一堆连接器。每个数据源一个同步脚本意味着要实现二十次“列出、获取、分页、处理删除”，且每个实现都有自己的 Bug。相反，应以声明式方式将每个数据源描述为数据映射（Datamap）——即一种关于其中存在内容的类型化层级结构。数据仓库是：连接 → 数据库 → 架构 → 表 → 列，每一层都挂载上下文类型；Wiki 是：空间 → 页面 → 块。

Once the hierarchy is data instead of code, one mining engine serves seven SQL warehouses without ever branching on a vendor’s name. Every mined artifact becomes a context item with identity derived from (tenant, type, path), which is what makes the system idempotent — your orchestrator will retry and workers will crash mid-batch.
一旦层级结构变成了数据而非代码，一个挖掘引擎就能服务七个 SQL 数据仓库，而无需针对不同供应商进行分支处理。每个挖掘出的工件都成为一个上下文条目，其身份由（租户、类型、路径）派生，这使得系统具有幂等性——你的编排器会重试，而工作节点可能会在批处理中途崩溃。

The loop is a coverage query: given the hierarchy and what’s in the store, what’s missing and what’s stale? Each type declares its own refresh cadence, and refreshes need their own queue — share one with first-time mining and a backlog will starve a newly connected source for days. This needs a durable workflow orchestrator, not because scheduling is hard but because deduplicating triggers, capping fan-out, and surviving crashes are.
循环的核心是一个覆盖率查询：给定层级结构和存储中的内容，什么缺失了？什么过期了？每种类型都声明了自己的刷新频率，且刷新需要独立的队列——如果与首次挖掘共享队列，积压的任务会让新连接的数据源数天无法同步。这需要一个持久化的工作流编排器，不是因为调度很难，而是因为去重触发器、限制扇出（Fan-out）以及在崩溃中恢复很难。

Deletion is the hardest part of sync. Things disappear through at least six channels: the source confirms removal, a parent’s manifest drops a child, a cursored record expires, a stale probe 404s, a re-walk finishes without seeing an item, a user disconnects a source. Worse, bounded collections (a table’s columns) and unbounded streams (tickets, PRs) need opposite semantics — manifest-diff deletion on a cursored stream wipes all history below the watermark; full-rescan tombstoning on a bounded collection wastes enormous work. Neither throws an error. Miss one channel and the brain confidently describes a table dropped in March.
删除是同步中最难的部分。事物会通过至少六种渠道消失：源确认删除、父级清单删除了子项、游标记录过期、陈旧探测返回 404、重新遍历未发现某项、用户断开数据源。更糟糕的是，有界集合（如表的列）和无界流（如工单、PR）需要相反的语义——在游标流上进行清单差异删除会抹除水印以下的所有历史记录；而在有界集合上进行全量扫描并标记删除则会浪费大量工作。两者都不会报错。漏掉任何一个渠道，大脑就会自信地描述一个三月份就被删除的表。

Mine behavior, not just structure. Query logs tell you which tables are alive versus abandoned and which joins analysts really use — and the best real queries, once validated, become golden queries: retrievable items worth more to a revenue question than any amount of schema metadata.
挖掘行为，而不仅仅是结构。查询日志会告诉你哪些表是活跃的，哪些是被废弃的，以及分析师真正使用了哪些连接（Join）——一旦经过验证，这些最真实的查询就变成了“黄金查询”：对于回答营收问题而言，它们比任何数量的架构元数据都更有价值。

Identity resolution comes first. A private channel’s member list names chat-platform user IDs; your ACLs speak in your own principals. Resolving them before mining permission-scoped content is a correctness constraint, not an optimization — ingest a restricted item before its principals resolve and you’ve either leaked it or hidden it from its rightful readers.
身份解析是首要任务。私有频道的成员列表列出的是聊天平台的 ID，而你的访问控制列表（ACL）使用的是你自己的主体（Principals）。在挖掘受权限限制的内容之前解析这些身份是一个正确性约束，而非优化手段——如果在主体解析完成前摄取了受限条目，你要么会导致数据泄露，要么会让合法的阅读者无法访问。

Connections break, and the map freezes silently. Tokens expire and grants narrow; mining doesn’t fail loudly, it just stops while users keep trusting a fossilized map. You need one per-connection state machine, fed by probes and error classification, that the orchestrator consults and the UI surfaces.
连接会中断，映射会悄无声息地冻结。Token 会过期，权限会收窄；挖掘过程不会大声报错，它只是停止了，而用户却还在信任一张已经“化石化”的映射图。你需要为每个连接建立一个状态机，由探测和错误分类提供输入，供编排器查询并在 UI 上呈现。

### Part 2: Indexing
### 第二部分：索引

There is no single index that serves a company brain. You need a source of truth plus a fan-out of rebuildable projections:
没有单一的索引能支撑起企业大脑。你需要一个事实来源（Source of Truth）加上一系列可重建的投影（Projections）：

*   **Relational ground truth.** Every item lives in a per-tenant Postgres schema. Writes commit here first, ACLs are enforced here last, every other index rebuilds from here. If you take one rule from this article: search indexes are caches, the database is the truth.
    **关系型事实来源。** 每个条目都存在于租户隔离的 Postgres 架构中。写入首先提交到这里，访问控制最后在这里执行，所有其他索引都从这里重建。如果你要从本文记住一条规则，那就是：搜索索引是缓存，数据库才是事实。
*   **A keyword index for lexical recall.** Users search for `dim_customers_v3`, and no embedding model ranks that reliably above `dim_customers_v2` on semantics alone. BM25 does.
    **用于词汇召回的关键词索引。** 用户搜索 `dim_customers_v3` 时，仅靠语义，没有任何嵌入模型能可靠地将其排在 `dim_customers_v2` 之上。但 BM25 可以。
*   **A vector index** — one collection for natural-language descriptions, another for code-like content such as validated SQL, with different embedding models. You only discover that split by measuring.
    **向量索引** —— 一个集合用于自然语言描述，另一个用于验证过的 SQL 等代码类内容，并使用不同的嵌入模型。只有通过测量，你才能发现这种拆分的必要性。
*   **A knowledge graph for structure:** containment, joins, dashboard→table lineage. “What breaks if I drop this table?” is a traversal; forcing it through similarity search is malpractice.
    **用于结构的知识图谱：** 包含关系、连接、仪表盘→表血缘。回答“如果我删除这张表会破坏什么？”是一个遍历问题；强行通过相似度搜索来解决是错误的实践。

Embedding pipelines are ETL, not a function call. Between truth and each projection sits a watermark-based sync, and enrichment comes first: a column named `f_stat_cd` needs an LLM-generated description before it’s worth embedding. Projections lag the truth, which is fine only if every pipeline has explicit cleanup phases and a rebuild runbook you’ve rehearsed.
嵌入流水线是 ETL，而不是函数调用。在事实来源和每个投影之间存在基于水印的同步，且丰富化（Enrichment）是第一位的：一个名为 `f_stat_cd` 的列在嵌入之前，需要先生成 LLM 描述才有意义。投影会滞后于事实，但这只有在每个流水线都有明确的清理阶段和经过演练的重建手册时，才是可以接受的。

Multi-tenancy shapes everything. Isolation should be physical, not a WHERE clause: schema, index, collection, and graph per tenant.
多租户架构决定了一切。隔离应该是物理层面的，而不是通过 `WHERE` 子句实现的：每个租户都应拥有独立的架构、索引、集合和图谱。
