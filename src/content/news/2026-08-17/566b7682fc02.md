# Designing a Persistent Knowledge Layer That Refuses to Guess
# 设计一个拒绝猜测的持久化知识层

**RAG Retrieves, It Never Remembers. A vendor-neutral blueprint for applications that accumulate understanding. Includes a complete Azure-native implementation (Microsoft Foundry, Azure AI Search, Cosmos DB, FastAPI) mapped to a property-insurance corpus.**

In my RAG-ING Ahead series I worked through a complete cloud-native retrieval stack: speech and document processing, chunking, embeddings, Azure AI Search, and an assistant layer sitting on top of it. That series answered the question I had at the time, which was essentially ‘how do I get a language model to answer questions about documents it was never trained on’?

在我的“RAG-ING Ahead”系列文章中，我完成了一套完整的云原生检索技术栈：语音和文档处理、分块（chunking）、嵌入（embeddings）、Azure AI Search，以及位于其上的助手层。该系列回答了我当时的问题，本质上就是：“如何让语言模型回答它从未训练过的文档相关问题？”

The stack still works. Retrieval-Augmented Generation remains the most practical way to ground a model in private, domain-specific or recently changed information without retraining anything. If you have a corpus and you need answers from it, RAG is still where you start.

这套技术栈依然有效。检索增强生成（RAG）仍然是将模型建立在私有、特定领域或近期变更信息基础上的最实用方法，且无需进行任何再训练。如果你拥有一个语料库并需要从中获取答案，RAG 依然是你的起点。

But I have been running that pattern for a while now, on projects that lasted longer than a demo, and a different question started to bother me: The system retrieves the same paragraph, reasons over it, produces a good answer — and then throws all that reasoning away. Tomorrow, someone asks a related question, and it does the identical work again, from scratch, at the same cost, with no guarantee of reaching the same conclusion.

但我已经运行这种模式一段时间了，在那些比演示项目更长期的项目中，一个不同的问题开始困扰我：系统检索出同一个段落，对其进行推理，得出一个好的答案——然后就把所有的推理过程丢弃了。明天，如果有人问一个相关的问题，它又会从零开始做同样的工作，花费同样的成本，且无法保证得出相同的结论。

My first instinct was to tune the machinery rather than question it. I experimented with different caching mechanisms based on embeddings: recognizing that an incoming question was semantically close to one the system had already answered, and serving the earlier response instead of paying for the full retrieval-and generation pass again. Semantic caching genuinely helps with cost and latency, and I would still recommend it. But it took me a while to admit what it actually is. It caches answers, not understanding. The cached response is exactly as disposable as the original one. Nothing about the system’s model of the domain has improved, and the moment a question falls outside the similarity threshold, the work starts from zero again.

我的第一直觉是去调整机器，而不是质疑它。我尝试了基于嵌入的不同缓存机制：识别出传入的问题在语义上与系统已经回答过的问题相近，并提供之前的响应，而不是再次支付完整的检索和生成费用。语义缓存确实有助于降低成本和延迟，我仍然推荐它。但我花了一段时间才承认它本质上是什么：它缓存的是答案，而不是理解。缓存的响应和原始响应一样是“一次性”的。系统对领域的模型没有任何改进，一旦问题超出了相似度阈值，工作又会从零开始。

Whatever I tweaked, the main RAG architectural concept underneath remained the same. Figure 1 – The semantic cache I was experimenting with. A hit is a shortcut past the pipeline; a miss starts from zero. Either way, nothing accumulates — the dashed box is the part that turned out to be missing. Image by author.

无论我如何调整，底层的核心 RAG 架构概念保持不变。图 1——我正在实验的语义缓存。命中（Hit）是绕过流水线的捷径；未命中（Miss）则从零开始。无论哪种方式，没有任何东西被积累下来——虚线框部分正是缺失的环节。图片由作者提供。

That is not a retrieval problem. Retrieval is doing exactly what it was designed to do. It is an architecture problem. There is nowhere in a standard RAG system for understanding to accumulate. No amount of caching, re-ranking or chunking strategy fixes that, because they all optimize the lookup, none of them gives the system a memory.

这不是一个检索问题。检索正在执行它被设计执行的任务。这是一个架构问题。在标准的 RAG 系统中，没有地方可以让“理解”积累下来。无论多少缓存、重排序或分块策略都无法解决这个问题，因为它们都只是优化了查找过程，没有一个能赋予系统记忆。

This article is about building that missing place. It is the result of my latest work and experimentation around RAG, GraphRAG and agentic reasoning over a corpus of documents, the point where the incremental tweaks stopped being enough and the design itself had to change.

本文旨在构建那个缺失的环节。这是我围绕 RAG、GraphRAG 以及针对文档语料库的代理推理（agentic reasoning）进行最新工作和实验的成果，此时增量式的调整已不再足够，设计本身必须做出改变。

I will present it in three parts. Part I is vendor-neutral. It describes the architecture as a design pattern: the layers, the object model, the failure modes it exists to survive, and the governance it demands. None of it depends on Azure, or on any particular database or model provider. If you are on AWS, GCP, or running Postgres with pgvector and a local model, the design still holds, and I would like it to be useful to you.

我将分三个部分进行介绍。第一部分是厂商中立的。它将架构描述为一种设计模式：层级、对象模型、它旨在应对的故障模式以及它所要求的治理。这一切都不依赖于 Azure，也不依赖于任何特定的数据库或模型提供商。如果你使用的是 AWS、GCP，或者运行带有 pgvector 的 Postgres 和本地模型，该设计依然适用，我希望它对你有用。

Part II is the Azure implementation. Service by service, with the reasoning for each choice, real infrastructure-as-code, and a running FastAPI application you can clone and deploy.

第二部分是 Azure 实现。逐个服务进行讲解，包含每个选择的理由、真实的基础设施即代码（IaC），以及一个你可以克隆并部署的运行中的 FastAPI 应用程序。

Part III is the demonstration. A synthetic property insurer called Ostermere Mutual, twenty-one interconnected documents, and three walkthroughs that show the pattern doing something a retrieval system genuinely cannot.

第三部分是演示。一个名为 Ostermere Mutual 的合成财产保险公司，包含二十一份相互关联的文档，以及三个演示，展示了该模式能够实现检索系统真正无法做到的事情。

Everything in the dataset is synthetic. Ostermere Mutual does not exist. Neither does the regulator, the policy, the claims, the people, the wind zones or the figures. Nothing here is insurance, legal, underwriting or claims advice, and no page in the demo represents a real interpretation of any real policy.

数据集中的一切都是合成的。Ostermere Mutual 并不存在。监管机构、保单、索赔、人员、风区或数据也都不存在。这里没有任何保险、法律、承保或索赔建议，演示中的任何页面也不代表对任何真实保单的真实解读。

Naming note: current Microsoft documentation uses Microsoft Foundry for the unified platform previously called Azure AI Foundry. I use Foundry throughout, while keeping the familiar Azure service names where they make the architecture easier to follow.

命名说明：当前的微软文档使用 Microsoft Foundry 来指代之前称为 Azure AI Foundry 的统一平台。我在全文中使用 Foundry，同时在使架构更易于理解的地方保留了熟悉的 Azure 服务名称。
