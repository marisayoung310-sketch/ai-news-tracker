# Loop Engineering for RAG Generation: An LLM Cascade from a Cheap Local Model Up to a Hosted Flagship
# RAG 生成的循环工程：从廉价本地模型到托管旗舰模型的 LLM 级联

You have a few hundred typed fields to pull out of a stack of real documents: amounts, dates, coverage limits, one structured value per field. The default reflex is to send every field to a GPT-4-class hosted API. It works, and the bill is the largest line in the pipeline’s running cost.
你有一堆真实文档，需要从中提取几百个特定类型的字段：金额、日期、承保限额，每个字段对应一个结构化数值。默认的反应是将每个字段都发送给 GPT-4 级别的托管 API。这确实有效，但账单却是整个流水线运行成本中最大的一笔开支。

Most of those fields are plain lookups a much smaller model handles fine, and you are paying flagship prices for all of them. The obvious reaction is to swap in a small model and pocket the savings. Done blindly, it backfires. A model too weak for the job returns broken typed output, or fumbles a transformation, and if nobody checks, the wrong value ships.
其中大多数字段只是简单的查找，小得多的模型完全可以胜任，但你却为所有字段支付了旗舰级的价格。显而易见的反应是换用一个小模型来节省开支。但如果盲目操作，结果会适得其反。如果模型能力不足，可能会返回格式错误的输出，或者在转换时出错；如果没有人进行检查，错误的数值就会被交付。

So the answer is not “use the big model” and it is not “use the small model”. It is to choose the model the way the earlier bricks choose a method: by criteria, then verify, and escalate only when the verification fails.
因此，答案既不是“使用大模型”，也不是“使用小模型”。而是像之前的模块选择方法那样去选择模型：根据标准进行判断，然后验证，仅在验证失败时才进行升级。

It develops one decision inside the generation brick: which model runs the call, and what happens when the cheap one is not good enough?
本文是《企业文档智能》系列的配套文章。该系列的理念在《放大专家能力》(Amplify the Expert) 一文中阐述，旨在通过四个模块构建企业级 RAG：文档解析、问题解析、检索和生成。本文深入探讨了生成模块中的一个决策：由哪个模型执行调用，以及当廉价模型表现不佳时该怎么办？

它借鉴了第 6C 篇（调度），该篇已能根据解析出的问题读取建议的模型层级；借鉴了第 8C 篇（验证），即触发升级的信号；以及第 10 篇（自适应解析），即将这种“先用廉价模型，按需升级”的模式应用于解析器。

### 1. Two angles: cost, and the loop
### 1. 两个视角：成本与循环

There are two reasons to care about model selection, and they reinforce each other. The cost angle is direct. Flagship models cost an order of magnitude more per call than a small local one. On an extraction job with thousands of field-level calls, or a corpus assistant answering thousands of questions a day, the model bill dominates the running cost. Most of those calls do not need a flagship. Routing the simple ones to a cheaper model is money left on the table until you do it.
关注模型选择有两个原因，且它们相辅相成。成本视角最为直接。旗舰模型每次调用的成本比小型本地模型高出一个数量级。在涉及数千次字段级调用的提取任务中，或者在每天回答数千个问题的语料库助手中，模型账单占据了运行成本的大头。其中大多数调用并不需要旗舰模型。将简单的调用路由到更便宜的模型，如果不这样做，就是白白浪费资金。

The loop angle is about correctness under that constraint. You cannot cut cost by guessing that a small model will cope. You start with a model, check whether its answer holds, and escalate to a stronger one only when the check fails. The loop is what makes the cost saving safe: the cheap model is the default attempt, not a gamble, because a failed attempt is caught and retried on a bigger model rather than shipped. Cost pushes you down the model ladder. The loop stops you from falling off it. This cheap-first, escalate-on-failure shape has a name in the literature: an LLM cascade.
循环视角关注的是在上述约束下的准确性。你不能通过猜测小模型能应付来降低成本。你需要先从一个模型开始，检查其答案是否成立，仅在检查失败时才升级到更强的模型。循环机制使得成本节约变得安全：廉价模型是默认尝试，而非一场赌博，因为失败的尝试会被捕获并由更大的模型重试，而不是直接交付。成本推动你向下选择模型，而循环则防止你从模型阶梯上跌落。这种“先用廉价模型，失败后升级”的模式在文献中被称为：LLM 级联 (LLM cascade)。

### 2. What the numbers say
### 2. 数据说明了什么

The design in Section 3 rests on two measured facts. Take them first, because they are the reason the cascade is shaped the way it is.
第 3 节的设计基于两个实测事实。先了解这些事实，因为它们正是级联模式如此设计的根本原因。

#### 2.1 The sweep: bigger is not better
#### 2.1 测评：越大并不越好

Look at what twenty local models did on the raw one-shot task: read the retrieved snippet, return the typed value. Same prompt, same fields, temperature 0. A 4B and a 7B top the local field, a 12B and a 14B sit below them, and a 1B is at the floor: size is a poor predictor.
看看二十个本地模型在原始单次提示任务中的表现：读取检索到的片段，返回类型化数值。相同的提示词，相同的字段，temperature 0。一个 4B 和一个 7B 模型在本地模型中表现领先，12B 和 14B 模型紧随其后，而 1B 模型处于垫底位置：模型大小并不是性能的良好预测指标。

Three conclusions come straight off that chart, and each one shapes the design. Bigger is not better. A 4B model (qwen3:4b) and a 7B (mistral:7b) top the local field. A 12B and a 14B (gemma3:12b, phi4:14b) sit below them. Two models from the same family, one twice the size of the other, tie. Parameter count is a poor predictor. The model family and how it was trained matter more. This is exactly why the loop must not climb a blind size ladder: the next rung up is often not the next size up.
从图表中可以直接得出三个结论，每一个都影响了设计。越大并不越好。一个 4B 模型 (qwen3:4b) 和一个 7B 模型 (mistral:7b) 在本地模型中表现最好。12B 和 14B 模型 (gemma3:12b, phi4:14b) 反而排在它们后面。同一系列中，一个模型大小是另一个的两倍，结果却打平。参数量是一个糟糕的预测指标。模型系列及其训练方式更为重要。这正是为什么循环机制不能盲目地按大小阶梯向上爬：更高一级的模型往往不是大小上的下一级。

There is a floor. The sub-2B models fall off a cliff (qwen2.5:1.5b at 12%, llama3.2:1b at 6%), and a 0.5B model we tried returned empty JSON on most fields: not a wrong answer, no answer at all. Starting there burns a loop iteration on a rung that was never going to hold. Criteria exist to start above the floor, not at it.
存在一个性能底线。2B 以下的模型表现断崖式下跌（qwen2.5:1.5b 为 12%，llama3.2:1b 为 6%），而我们尝试的一个 0.5B 模型在大多数字段上返回了空 JSON：这不是错误的答案，而是根本没有答案。从这些模型开始只会浪费一次循环迭代，因为它们根本无法胜任。必须设定标准从底线之上开始，而不是从底线开始。

Cost is not speed. The hosted flagship answered in about 1.4 seconds per field, faster than most local 7B-to-14B models (roughly 2.6 to 7.6 seconds each on a single consumer GPU). The small-local play buys a lower bill and documents that never leave the machine. It does not buy latency. If speed is the constraint, the cheap local model is often the wrong default, and that belongs in the dispatcher’s criteria.
成本不等于速度。托管旗舰模型每个字段的响应时间约为 1.4 秒，比大多数本地 7B 到 14B 模型（在单块消费级 GPU 上约为 2.6 到 7.6 秒）更快。使用小型本地模型可以降低账单，并确保文档不出本地机器，但它并不能带来低延迟。如果速度是约束条件，廉价本地模型往往不是正确的默认选择，这应纳入调度器的判断标准中。

One more sobering number. The best small local model, run on its own on the raw task, got roughly a third of the fields right. Fast (a few seconds a field) and not good enough to ship. A small local model is viable only when the loop backs it: a tight retrieval snippet, the right prompt content, validation on every field, and code doing the hard formatting.
还有一个令人清醒的数据。最好的小型本地模型在原始任务中独立运行时，大约只有三分之一的字段正确。虽然速度快（每个字段几秒），但不足以交付。小型本地模型只有在循环机制的支持下才可行：即精准的检索片段、正确的提示词内容、对每个字段的验证，以及负责复杂格式化的代码。
