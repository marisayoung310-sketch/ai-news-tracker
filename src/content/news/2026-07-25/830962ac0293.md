# Context Windows Forget What Matters — I Built a Usage-Reinforced Decay Engine for AI Agent Memory
# 上下文窗口会遗忘重要信息——我为 AI 智能体内存构建了一个基于使用频率的衰减引擎

How to build a usage-reinforced memory decay engine for AI agent memory that outperforms naive recency-window pruning on long-running, multi-session tasks — with a deterministic, zero-dependency Python implementation you can verify yourself.
如何构建一个基于使用频率的 AI 智能体内存衰减引擎，使其在长时间、多会话任务中表现优于简单的“最近窗口”修剪算法——并附带可自行验证的确定性、零依赖 Python 实现。

TL;DR: Most long-running AI agent memory systems evict old context using a sliding window: if something hasn’t been touched in N turns, it’s gone. This treats a foundational fact stated once on turn 1 and a throwaway debug log from turn 40 as identical — whichever is older loses, no matter how many times either one has actually been used. I built a memory engine that scores retention using the Ebbinghaus forgetting curve, where every recall reinforces an item’s stability and pushes its eviction horizon out non-linearly. Across 50 seeded sessions, it held a 100% Foundational Recall Rate against a 0% rate for the recency-only baseline — and I traced the exact mathematical reason why, then found the specific failure case where its advantage disappears entirely.
简而言之：大多数长时间运行的 AI 智能体内存系统使用滑动窗口来剔除旧上下文：如果某条信息在 N 轮对话内未被触及，它就会被删除。这种机制将第 1 轮提到的基础事实与第 40 轮的临时调试日志视为同等重要——无论谁更旧，谁就会被淘汰，而不考虑它们实际被使用的频率。我构建了一个使用艾宾浩斯遗忘曲线来评估保留率的内存引擎，其中每次调用都会增强项目的稳定性，并以非线性方式推迟其被剔除的时间点。在 50 组种子会话测试中，该引擎的基础事实召回率达到了 100%，而仅基于“最近原则”的基准测试则为 0%——我追踪了其背后的确切数学原理，并找出了其优势完全消失的特定失败场景。

### Key Takeaways
### 核心要点

The issue here is structural, not something you can tune your way out of. With a fixed recency window, you hit a hard mathematical wall: if you don’t touch an item within window_size turns, it’s wiped from memory. It doesn’t matter if it was the most heavily used item in the system five minutes ago—once it slips past that window, it’s gone.
这个问题是结构性的，无法通过简单的参数调整来解决。使用固定的“最近窗口”，你会遇到一道硬性的数学墙：如果你在窗口大小（window_size）轮次内没有触及某项内容，它就会从内存中被抹除。即便它五分钟前还是系统中被使用最频繁的项目，一旦滑出窗口，它就消失了。

Second, reinforcement compounds where recency fails. By letting retention scale with recall frequency, the decay engine pushes an item’s effective survival horizon out by orders of magnitude based on just a few early interactions.
其次，在“最近原则”失效的地方，强化机制发挥了作用。通过让保留率随调用频率缩放，衰减引擎仅凭早期的几次交互，就能将项目的有效存活期延长几个数量级。

Third, let’s be clear: this isn’t “better memory” across the board. To make sure this wasn’t a benchmark artifact, I built a failure-case test. When a fact is introduced once and never recalled, the decay engine performs identically to the baseline. That is the honest boundary of this mechanism.
第三，必须明确：这并非在所有方面都“更优”。为了确保这不是基准测试的伪影，我构建了一个失败案例测试。当一个事实只被引入一次且从未被再次调用时，衰减引擎的表现与基准测试完全一致。这就是该机制诚实的边界。

Fourth, it is entirely deterministic. Everything relies on an explicit turn counter, not wall-clock time. To verify, I ran the suite on two different machines and operating systems—the diffed outputs were byte-identical.
第四，它是完全确定性的。一切都依赖于明确的轮次计数器，而不是挂钟时间。为了验证，我在两台不同的机器和操作系统上运行了测试套件——输出结果的差异对比显示它们是字节级一致的。

Finally, always audit your benchmarks. Two hidden bugs almost invalidated this entire run. I’m breaking them down because catching these issues is the difference between data you can trust and data that quietly lies to you.
最后，务必审计你的基准测试。两个隐藏的 Bug 差点让整个测试失效。我将详细拆解它们，因为发现这些问题是区分“可信数据”与“悄悄欺骗你的数据”的关键。

### The Fact That Outlived Its Own Window
### 那些超越了自身窗口寿命的事实

Let’s look at how this actually plays out in practice. Imagine you are 150 turns into a session with an agent. On the very first turn, the user gives the agent a core rule, like a compliance requirement or a specific tech stack constraint. The agent references it a few times during the first thirty turns while getting oriented, but then the conversation moves on. For the next hundred turns, the agent is busy doing other things, like parsing logs, making one-off tool calls, and handling random side tasks. Later in the session, well past that early window, you ask a question that depends entirely on that rule from turn one.
让我们看看这在实践中是如何发生的。想象一下，你与智能体的会话已经进行了 150 轮。在第一轮，用户给了智能体一条核心规则，比如合规要求或特定的技术栈约束。智能体在最初的 30 轮中为了适应环境引用了几次该规则，但随后对话转向了其他话题。在接下来的 100 轮中，智能体忙于处理其他事情，如解析日志、进行一次性工具调用以及处理随机的辅助任务。在会话后期，远超最初的窗口期后，你提出了一个完全依赖于第一轮那条规则的问题。

With a standard sliding window, you have already lost that rule. The window doesn’t know the rule is critical, and it doesn’t care that the agent already used it five times. It just sees a turn count that got too high and drops the data. That isn’t memory. It is just a countdown timer.
使用标准的滑动窗口，你已经丢失了那条规则。窗口不知道该规则至关重要，也不在乎智能体之前已经使用过它五次。它只看到轮次计数过高，然后就丢弃了数据。那不是内存，那只是一个倒计时器。

I ran this exact scenario across 50 seeded sessions. In this benchmark, the decay engine retained every foundational fact through the end of the session, while the recency-only baseline retained none. The result was consistent across all 50 seeds. Here is why that happens.
我在 50 组种子会话中运行了完全相同的场景。在这个基准测试中，衰减引擎在会话结束时保留了所有基础事实，而仅基于“最近原则”的基准测试则一个都没保留。这一结果在所有 50 组种子测试中保持一致。这就是原因所在。

### Who This Is For
### 适用人群

This approach applies to any system where an agent needs to keep context across a long, multi-turn session. Think of coding agents working on multi-day tasks, customer support bots handling extended troubleshooting threads, autonomous research loops, or any pipeline where memory has to mean more than just the last few messages.
这种方法适用于任何需要跨越长、多轮会话保持上下文的系统。例如：处理多日任务的编程智能体、处理长故障排查线程的客户支持机器人、自主研究循环，或任何需要内存不仅仅是“最后几条消息”的流水线。

You can skip this entirely if your sessions are short enough that everything fits into the context window anyway. You also do not need it if every fact in your session has roughly equal relevance the whole time. A simple window works fine for that, and there is no point building a solution for a problem you do not have.
如果你的会话足够短，所有内容都能放入上下文窗口，你可以完全跳过此方案。如果会话中的每个事实在整个过程中相关性大致相同，你也不需要它。简单的窗口机制就足够了，没必要为你没有的问题去构建解决方案。

### Why This Matters for Real Systems
### 为什么这对实际系统很重要

This is not just an abstract issue for benchmarks. You see this exact pattern play out in production all the time. Take coding agents as an example. If an agent is working on a task over several days, it might get a strict instruction on day one, like a specific library version to use or a file it should never edit. Once the session gets too long, a naive recency window just drops that instruction, and the agent breaks your codebase.
这不仅仅是基准测试中的抽象问题。你在生产环境中会不断看到这种模式。以编程智能体为例，如果智能体在几天内处理一项任务，它可能在第一天就收到严格指令，比如使用特定的库版本或绝对不能编辑的文件。一旦会话变得太长，简单的“最近窗口”就会丢弃该指令，导致智能体破坏你的代码库。

Or take customer support bots. If a troubleshooting thread goes on too long, the back-and-forth piles up until the bot completely forgets the user’s account details or the actual problem they started with. Next thing you know, the bot is asking questions the user already answered ten minutes ago.
再看客户支持机器人。如果故障排查线程持续时间过长，对话堆积起来，直到机器人完全忘记用户的账户详情或最初的问题。接下来你会发现，机器人开始询问用户十分钟前已经回答过的问题。

You see the same issue in RAG pipelines. The system aggressively throws out facts just because they haven’t been mentioned in the last few turns. It doesn’t matter if those facts are central to the entire task and crucial for the final steps; if they aren’t active right now, they get pruned. When these systems fail, they don’t crash or throw clean errors. They just quietly hand you a wrong or incomplete answer because the one piece of information that actually mattered...
在 RAG（检索增强生成）流水线中也会出现同样的问题。系统仅仅因为某些事实在最近几轮中未被提及，就激进地将其丢弃。无论这些事实对整个任务是否核心、对最终步骤是否关键，只要它们当前不活跃，就会被修剪。当这些系统失败时，它们不会崩溃或抛出明确的错误，只是悄悄地给你一个错误或不完整的答案，因为那个真正重要的信息……
