# Build and Run an Intelligent Document Processing (IDP) System in the Cloud
# 在云端构建并运行智能文档处理 (IDP) 系统

**Automating the classification and extraction of PII from emails using AWS**
**使用 AWS 自动化处理电子邮件中的个人身份信息 (PII) 分类与提取**

Thomas Reid | Jul 24, 2026 | 14 min read

In my last job, I built a fully automated intelligent document processing (IDP) system that ran in the cloud on Amazon Web Services. The system was designed to allow Freedom of Information-type requests from Irish citizens wanting to know whether their details (name, address, etc.) were recorded in a large insurance claims database maintained by my employer.
在我上一份工作中，我构建了一个在亚马逊云科技 (AWS) 上运行的全自动化智能文档处理 (IDP) 系统。该系统旨在处理爱尔兰公民提出的“信息自由”类请求，他们希望了解自己的个人信息（姓名、地址等）是否被记录在我雇主维护的大型保险理赔数据库中。

At a high-level, the workflow schedule was this: Client solicitors sent an email to a specific Outlook address requesting a search of the client’s details in the database. For the search, we needed the first and last name of the client, together with their date of birth and current address. A search could only proceed if there were corroborating documents attached to the email to “prove” who the client was. The attachments would typically be PDFs containing images of passports, driving licences, and other official documents. In addition, we could also receive MS Word documents or PDFs of bank statements and utility bills.
从宏观层面来看，工作流程如下：客户律师向指定的 Outlook 地址发送电子邮件，请求在数据库中搜索客户的详细信息。为了进行搜索，我们需要客户的姓名、出生日期和当前地址。只有当电子邮件中附有证明客户身份的佐证文件时，搜索才能进行。附件通常是包含护照、驾照及其他官方证件图像的 PDF 文件。此外，我们还会收到银行对账单和水电费账单的 Word 文档或 PDF 文件。

At a specified time each day, the IDP processed these emails, extracted and classified the attachments and extracted any relevant Personally Identifiable Information (PII), which was sent to a claims database for searching. If claim details were found in the database, a password-protected PDF containing those details was created and sent back to the solicitor, along with a separate email containing the password to unlock it. If no results were found, a simple email was sent back indicating this.
每天在指定时间，IDP 系统会处理这些邮件，提取并分类附件，同时提取相关的个人身份信息 (PII)，并将其发送至理赔数据库进行搜索。如果在数据库中找到了理赔详情，系统会生成一个受密码保护的 PDF 文件并发送回给律师，同时通过另一封邮件发送解锁密码。如果没有找到结果，则会回复一封简单的邮件告知对方。

Apart from a Human-In-The-Loop (HIL) process that allowed users to perform a final cross-check as to whether the PII extracted from different documents matched, the process was fully automated. Incidentally, this new process proved approximately 90% more efficient than the manual system it replaced.
除了一个允许用户进行最终交叉核对（确认从不同文档中提取的 PII 是否匹配）的“人在回路”(HIL) 环节外，整个流程是完全自动化的。顺便提一下，事实证明，这一新流程比它所取代的人工系统效率提高了约 90%。

In this article, I’m going to show you the steps I took to implement this system on the AWS cloud platform, albeit a slightly simplified version of it. Note that apart from being a user of Amazon Web Services (AWS), I have no affiliation or association with the company.
在本文中，我将向您展示我在 AWS 云平台上实现该系统的步骤，尽管这是一个稍微简化后的版本。请注意，除了作为亚马逊云科技 (AWS) 的用户外，我与该公司没有任何隶属或关联关系。

In the real system I developed, our source of emails came from a corporate Outlook email account. I don’t have access to one of those now, so instead, I’ll use my personal Gmail as our email server and assume each email contains only one attachment. I’m assuming that any attachment will always be an image file (JPG or PNG) of a passport, driving licence, or bank statement. Also, the final step in our process will be a simple result file on S3 that indicates the classification and PII extraction values for the attachment.
在我开发的实际系统中，邮件来源是企业 Outlook 邮箱。我现在无法访问该账户，因此我将改用我的个人 Gmail 作为邮件服务器，并假设每封邮件仅包含一个附件。我假设所有附件均为护照、驾照或银行对账单的图像文件 (JPG 或 PNG)。此外，我们流程的最后一步是在 S3 上生成一个简单的结果文件，显示附件的分类结果和提取出的 PII 数值。

As this is mainly about the AWS side of things, I’m going to assume that everything is set up in your email client to enable an AWS Lambda process to read your emails. For Gmail, briefly, this process would include: creating or selecting a Google Cloud project, enabling the Gmail API, and enabling OAuth and completing a one-time Google consent flow. After that, you would store the returned credentials/refresh tokens securely in something like AWS Secrets Manager.
由于本文主要关注 AWS 相关内容，我假设您已经在邮件客户端完成了相关设置，以便 AWS Lambda 能够读取您的邮件。对于 Gmail，简而言之，该过程包括：创建或选择一个 Google Cloud 项目、启用 Gmail API、启用 OAuth 并完成一次性的 Google 同意流程。之后，您需要将返回的凭据/刷新令牌安全地存储在 AWS Secrets Manager 等服务中。

The goal is to extract the following pieces of PII from each email attachment: Document Type, First Name, Last Name, DoB and Address.
我们的目标是从每个邮件附件中提取以下 PII 信息：文档类型、名字、姓氏、出生日期和地址。

### 1/ Storing our OAUTH credentials securely
### 1/ 安全存储 OAUTH 凭据

The first thing we need to do is store our Gmail OAuth credentials and refresh token in AWS Secrets Manager. For me, my email setup returned a JSON document that looked like this:
我们需要做的第一件事是将 Gmail OAuth 凭据和刷新令牌存储在 AWS Secrets Manager 中。就我而言，我的邮件设置返回的 JSON 文档如下所示：

```json
{
  "installed": {
    "client_id": "my_client_id.apps.googleusercontent.com",
    "client_secret": "MY_CLIENT_SECRET",
    "project_id": "my_project_id",
    "auth_uri": "https://accounts.google.com/o/oauth2/auth",
    "token_uri": "https://oauth2.googleapis.com/token"
  }
}
```

Open the AWS management console and go to the Secret Manager screen. Click the “Store a new secret” button and choose “Other type of secret” as the secret type. Under the key/values pairs section, select the Plaintext TAB and enter your JSON from above. So your screen should look like this. Click Next, then enter a suitable name and description for your new secret. Click Next, then Next again, before clicking the Store button.
打开 AWS 管理控制台并进入 Secrets Manager 页面。点击“Store a new secret”（存储新密钥）按钮，选择“Other type of secret”（其他类型的密钥）。在键值对部分，选择“Plaintext”（纯文本）选项卡并输入上述 JSON 内容。您的屏幕应该看起来像这样。点击“Next”（下一步），输入合适的密钥名称和描述。再次点击“Next”，最后点击“Store”（存储）按钮。

### 2/ Set up our S3 buckets
### 2/ 设置 S3 存储桶

We’ll have one general-purpose bucket and 5 folders that will hold our data:
我们将创建一个通用存储桶和 5 个用于存放数据的文件夹：

*   **raw**: this is where the raw email attachments will be downloaded to (存放原始邮件附件)
*   **textract**: this will hold the text returned by Textract (存放 Textract 返回的文本)
*   **results**: this will hold the results of the document classification and PII information (存放文档分类和 PII 信息结果)
*   **audit**: logging information (存放日志信息)
