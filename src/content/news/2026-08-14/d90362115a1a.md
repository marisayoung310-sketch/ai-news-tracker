# How to Utilize OKF Efficiently to Enable Knowledge Exchange Among LLMs
# 如何高效利用 OKF 实现大模型间的知识交换

Large Language Models How to Utilize OKF Efficiently to Enable Knowledge Exchange Among LLMs Take Google's Open Knowledge Format (a Markdown+YAML skeleton for humans and agents), bolt one extra load-bearing field onto the frontmatter, and hand pre-tokenized integer arrays between three Qwen2.5-Coder agents (7B, 3B, 1.5B) through `/dev/shm`. 28–37% faster TTFT — and one runtime check that stands between "faster" and "confidently fluent nonsense."

大语言模型如何高效利用 OKF 实现模型间的知识交换？只需采用 Google 的 Open Knowledge Format（一种面向人类和智能体的 Markdown+YAML 骨架），在 Frontmatter 中增加一个关键字段，并通过 `/dev/shm` 在三个 Qwen2.5-Coder 智能体（7B、3B、1.5B）之间传递预分词的整数数组。这能带来 28–37% 的首字延迟（TTFT）提升，同时通过一道运行时检查，确保系统不会在“速度提升”与“一本正经地胡说八道”之间失控。

### Key Takeaways
### 核心要点

**The pattern.** This is Google’s Open Knowledge Format skeleton — a Markdown file with a YAML frontmatter block — repurposed for agent hand-off. The repo’s frontmatter carries one extra load-bearing field the general OKF spec does not define: `token_pointer`, an absolute path to the pre-computed .npy array in shared memory. Human-readable body, machine-readable pointer.

**模式：** 这是 Google 的 Open Knowledge Format 骨架——一个带有 YAML Frontmatter 块的 Markdown 文件——被重新用于智能体之间的数据交接。该仓库的 Frontmatter 包含了一个通用 OKF 规范中未定义的关键字段：`token_pointer`，即共享内存中预计算好的 `.npy` 数组的绝对路径。实现了人类可读的正文与机器可读的指针相结合。

**The mechanism.** Three Qwen2.5-Coder models of different sizes (7B / 3B / 1.5B) cannot share a KV cache — they have different architectures. But they can share pre-computed token IDs, because the whole Qwen2.5-Coder family ships one identical BPE vocabulary. This repo tokenizes once, hands off the integer array through `/dev/shm/qwen_tokens/`, and lets every downstream agent skip its own tokenizer entirely on the input side.

**机制：** 三个不同规模的 Qwen2.5-Coder 模型（7B / 3B / 1.5B）无法共享 KV 缓存，因为它们的架构不同。但它们可以共享预计算的 Token ID，因为整个 Qwen2.5-Coder 系列使用完全相同的 BPE 词表。该仓库实现了一次分词，通过 `/dev/shm/qwen_tokens/` 传递整数数组，让下游的每个智能体在输入端完全跳过自身的 Tokenizer。

**The numbers.** Median of 7 trials per prompt, 3 blocks, greedy decoding, 64 new tokens: on the 3B model, mean baseline TTFT drops from 69.3 ms to 49.9 ms — a 28.0% reduction. On the 1.5B model, from 49.6 ms to 30.9 ms — a 37.8% reduction. Both models pass the coherence heuristic on every sample. Full pipeline wall clock is 41.3 s end to end (Agent 1: 3.9 s, Agent 2: 18.7 s, Agent 3: 15.7 s).

**数据：** 在每个提示词 7 次试验、3 个块、贪婪解码、生成 64 个新 Token 的测试中：3B 模型平均 TTFT 从 69.3 毫秒降至 49.9 毫秒，降低了 28.0%；1.5B 模型从 49.6 毫秒降至 30.9 毫秒，降低了 37.8%。两个模型在每个样本上均通过了连贯性启发式检查。完整流水线端到端耗时 41.3 秒（智能体 1：3.9 秒，智能体 2：18.7 秒，智能体 3：15.7 秒）。

**The guardrail.** Feeding a downstream model an integer array that meant a different subword under its own vocabulary does not crash anything. It generates a fluent, coherent-looking, completely wrong report. So before any agent trusts another agent’s integers, this pipeline runs a full ~151,936-entry `get_vocab()` dict equality check — not a vocab_size comparison, the real thing.

**护栏：** 如果向下游模型输入一个在其自身词表中代表不同子词的整数数组，程序不会崩溃，但会生成一份看起来流畅、连贯但内容完全错误的报告。因此，在任何智能体信任另一个智能体的整数数组之前，该流水线会运行一次完整的约 151,936 条目的 `get_vocab()` 字典相等性检查——这不是简单的词表大小比较，而是真正的逐项比对。

### 1. A confession: your second agent is doing your first agent’s homework, twice
### 1. 坦白：你的第二个智能体正在重复做第一个智能体的作业

Let me dramatise the moment this whole repo is about. Imagine you have three LLM agents chained together. Agent 1 is a big model, it reads a design document. Agent 2 is a mid-sized model, it evaluates part of it. Agent 3 is a small model, it writes the final report. All three of them come from the same model family — same tokenizer, same vocabulary, same everything above the hidden layers — just at three different sizes.

让我来演绎一下这个仓库所解决的核心场景。想象你有三个串联的大模型智能体。智能体 1 是大模型，负责阅读设计文档；智能体 2 是中型模型，负责评估部分内容；智能体 3 是小型模型，负责撰写最终报告。这三个模型来自同一个家族——相同的分词器、相同的词表、隐藏层以上的一切都相同——只是规模不同。

Since you are not made of H100s, and running a 7B model three times when a 1.5B model will do for the last step would be, frankly, rude to your GPU. Now watch what happens on a naive setup:

既然你不可能拥有无限的 H100 显卡，而且在最后一步明明可以用 1.5B 模型的情况下还去运行 7B 模型，坦白说，这对你的 GPU 是一种浪费。现在看看在原始设置下会发生什么：

**You:** “Agent 1, please read this design document and pass the relevant sections to Agent 2.”
**你：** “智能体 1，请阅读这份设计文档，并将相关部分传给智能体 2。”

**Agent 1 (7B):** “On it. Loading tokenizer. Running BPE over the whole document. Sections split. Handing off the interesting sections to Agent 2 as strings. ✅”
**智能体 1 (7B)：** “收到。正在加载分词器。对整个文档运行 BPE。已拆分章节。将相关部分以字符串形式传给智能体 2。✅”

**You:** “Great. Agent 2?”
**你：** “很好。智能体 2？”

**Agent 2 (3B):** “Hello, I am a beautiful, stateless newborn. Loading my own tokenizer. Running BPE over the same characters Agent 1 already ran BPE over three seconds ago. Writing an evaluation.”
**智能体 2 (3B)：** “你好，我是一个全新的、无状态的智能体。正在加载我自己的分词器。正在对智能体 1 三秒前刚刚处理过的相同字符运行 BPE。正在撰写评估。”

**You:** “Wait, you have the exact same tokenizer as Agent 1.”
**你：** “等等，你和智能体 1 使用的是完全相同的分词器。”

**Agent 2 (3B):** “I do?”
**智能体 2 (3B)：** “是吗？”

**You:** “Yes. You are literally in the same model family. Same vocabulary, same subword IDs, same everything.”
**你：** “是的。你们属于同一个模型家族。相同的词表，相同的子词 ID，一切都一样。”

**Agent 2 (3B):** “That’s nice. Anyway, I have re-tokenized the input from scratch and I am ready to generate. Please stand by. 🫡”
**智能体 2 (3B)：** “那挺好。总之，我已经从头重新分词完毕，准备开始生成。请稍候。🫡”

**You:** “…and Agent 3?”
**你：** “……那智能体 3 呢？”

**Agent 3 (1.5B):** “Loading tokenizer. Running BPE over Agent 2’s output—”
**智能体 3 (1.5B)：** “正在加载分词器。正在对智能体 2 的输出运行 BPE——”

**You:** “You know what, forget I asked.”
**你：** “算了，当我没问。”

That is the joke, and it is the dirty secret of every multi-agent LLM pipeline that fans out over one shared piece of text using models from the same family. The tokenizer is not the bottleneck — a fast Rust-backed BPE tokenizer is not slow, and I will not lie to you and pretend it is. But the tokenizer is redundant work, and how many times you do redundant work is not a function of how fast the redundant work is. It is a function of how many downstream consumers you fanned out to.

这就是这个笑话的由来，也是每一个使用同家族模型、针对同一文本进行多智能体协作的 LLM 流水线中不为人知的“脏秘密”。分词器本身并不是瓶颈——基于 Rust 的快速 BPE 分词器并不慢，我不会欺骗你说它慢。但分词是冗余工作，而你执行冗余工作的次数，并不取决于冗余工作本身有多快，而是取决于你有多少个下游消费者。
