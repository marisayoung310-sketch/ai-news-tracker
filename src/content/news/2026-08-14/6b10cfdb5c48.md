# Cut an Enterprise RAG Pipeline’s Latency and Cost by Calling the LLM Less, Not by Buying a Faster Model
# 通过减少大模型调用次数（而非购买更快的模型）来降低企业级 RAG 流水线的延迟与成本

Large Language Model Cut an Enterprise RAG Pipeline’s Latency and Cost by Calling the LLM Less, Not by Buying a Faster Model Enterprise Document Intelligence [Vol.1 #9ter] – The pipeline from Article 9 calls a model at several steps to be sure it is right. On easy questions that is needless latency. A per-question signal routes them past the model, about two seconds saved for a keyword match.
大语言模型通过减少调用次数而非购买更快的模型来降低企业级 RAG 流水线的延迟与成本。企业文档智能 [第1卷 #9ter] —— 第9篇文章中的流水线在多个步骤中调用模型以确保准确性。对于简单问题，这会导致不必要的延迟。通过针对每个问题的信号，可以将简单问题绕过模型处理，对于关键词匹配任务，大约可节省两秒钟。

More and more, RAG pipelines are built the agentic way: put a model wherever a decision needs judgment, and let it decide. That means a lot of model calls. The pipeline from Article 9 (a production RAG pipeline for PDFs) is built exactly like that. Ask “What is the annual premium?” and it runs three model calls in series: one to parse the question, one to arbitrate the retrieved candidates, one to generate the typed answer.
越来越多的 RAG 流水线采用代理（Agentic）方式构建：在任何需要判断的地方放置一个模型，并让它做决定。这意味着大量的模型调用。第9篇文章中的流水线（一个用于 PDF 的生产级 RAG 流水线）正是这样构建的。当询问“年度保费是多少？”时，它会串行运行三次模型调用：一次用于解析问题，一次用于仲裁检索到的候选内容，一次用于生成格式化的答案。

Each call buys something real. The parsing call absorbs typos and vague phrasing before retrieval runs. The arbiter call keeps a wrong page from reaching generation. The generation call returns a typed answer with a quote you can check on the page. On a hard question, these three calls are what make the answer trustworthy, and that is why Article 9 put them there.
每一次调用都有其实际价值。解析调用在检索运行前处理了拼写错误和模糊措辞。仲裁调用防止了错误页面进入生成阶段。生成调用返回一个带有可供页面核对引用的格式化答案。对于难题，这三次调用是答案可信度的保障，这也是第9篇文章将其包含在内的原因。

The problem is that we cannot afford this on every question, because it is slow. Three calls in series means the user waits about two seconds, and pays tokens, on every question, easy ones included. And many enterprise questions were never hard: “What is the annual premium?” has one answer, on one line, and the deterministic keyword match had already isolated it on the first pass.
问题在于，我们无法在每个问题上都这样做，因为它太慢了。三次串行调用意味着用户在每个问题（包括简单问题）上都要等待约两秒钟，并支付 Token 费用。而许多企业级问题根本不难：“年度保费是多少？”只有一个答案，位于一行中，确定性的关键词匹配在第一轮检索时就已经将其定位到了。

So this article adds a router: a cheap per-question signal, read before any model call, that sends easy questions down the fast path and keeps all three calls for the hard ones. This article is the map of that routing: the signal (a score the pipeline already computes), the margin that makes it honest, what it saves (about two seconds on a keyword match), and the questions it must refuse to fast-path.
因此，本文增加了一个路由器：一个廉价的“逐问题”信号，在任何模型调用之前读取，将简单问题发送到快速路径，而将所有三次调用保留给难题。本文是该路由机制的指南：信号（流水线已计算出的分数）、确保其准确性的阈值、节省的时间（关键词匹配约节省两秒），以及必须拒绝快速处理的问题。

Every number is a real run on the fictional broker corpus, reproducible in the companion notebook.
文中的每一个数字都是在虚构的经纪人语料库上运行的真实结果，可在配套的 Notebook 中复现。

### 1. Every question pays for the whole pipeline
### 1. 每个问题都要为整个流水线买单

The upgraded pipeline is worth its cost on hard questions. The problem is that it charges the same cost on easy ones. Trace a single question through it and the model calls stack up: one to normalize the question and pull its keywords, one for the arbiter that ranks the retrieved candidates, one to generate the typed answer. Three round-trips to a hosted model, in series, before the user sees a word.
升级后的流水线在处理难题时物有所值。问题在于，它在处理简单问题时也收取同样的成本。追踪一个问题在其中的处理过程，模型调用会堆叠起来：一次用于规范化问题并提取关键词，一次用于对检索到的候选内容进行排序的仲裁器，一次用于生成格式化答案。在用户看到任何文字之前，需要与托管模型进行三次串行往返。

On a hard question that is money well spent. On “what is the premium?” it is three network hops to return a value that a keyword match had already isolated on the first pass. The latency is real and it is the part the user feels. The token cost is smaller per call, but it is billed on every question, forever, and the easy questions are the ones users repeat most.
对于难题，这钱花得值。但对于“保费是多少？”这类问题，这相当于进行了三次网络往返，只为了返回一个关键词匹配在第一轮就已经定位到的值。延迟是真实存在的，也是用户能直接感受到的部分。虽然每次调用的 Token 成本较低，但它在每个问题上都会持续计费，而简单问题恰恰是用户重复提问最多的。

Before any of those three calls fire, the pipeline can make one decision with no model call, from the parsed question and the document’s line_df: can this question be answered on the keyword path alone? The decision needs a signal. It has to be cheap, because the whole point is to spend nothing when the answer is easy, and it has to be honest, because a router that sends a hard question down the fast path returns a confident wrong answer, the exact failure the series works to avoid.
在上述三次调用触发之前，流水线可以根据解析后的问题和文档的 `line_df`（行数据框）在不调用模型的情况下做出一个决定：这个问题能否仅通过关键词路径回答？这个决定需要一个信号。它必须是廉价的，因为我们的目的就是在答案简单时零成本处理；它也必须是诚实的，因为如果路由器将难题误导至快速路径，会返回一个自信的错误答案，这正是本系列文章极力避免的故障。

### 2. Not every question needs the model
### 2. 并非每个问题都需要模型

The signal is already in the pipeline. Retrieval scores each line by how strongly the question’s keywords co-occur on it, and that score, before any arbiter or generation call, already separates the questions that answer themselves from the ones that do not.
信号其实已经在流水线中了。检索过程会根据问题关键词在每一行中的共现强度对每一行进行评分，而在任何仲裁或生成调用之前，该分数就已经将“自明问题”（答案显而易见的问题）与需要模型的问题区分开了。

#### 2.1 A question that answers itself
#### 2.1 自明问题

Take “what is the annual premium?” against a homeowner’s policy. The deterministic keyword scorer from Article 7 (retrieval as filtering on line_df), co_occurrence_score, counts how many of the question’s keywords land on each line, weighting a primary term (premium) together with the co-signals that mark a real answer (EUR, annual, payable). Run it and one line wins outright.
以针对一份房主保单询问“年度保费是多少？”为例。第7篇文章中的确定性关键词评分器（将检索视为对 `line_df` 的过滤）`co_occurrence_score` 会计算问题的关键词在每一行中出现的次数，并对主要术语（保费）以及标记真实答案的共现信号（欧元、年度、应付）进行加权。运行后，有一行会以绝对优势胜出。

The top line, “The annual premium is EUR 1,200, payable…”, scores 5. Every other line scores 0. One clear winner, a margin of 5 over the runner-up, and the winning line already carries the shape of the answer, a currency and an amount. There is nothing for the model to disambiguate. The keyword path has answered the question, and a generation call here would only reformat a value that is already isolated.
得分最高的那一行“年度保费为 1,200 欧元，应付……”，得分为 5。其他所有行得分为 0。有一个明显的赢家，比第二名高出 5 分，且胜出的这一行已经包含了答案的形态：货币和金额。模型无需进行任何消歧。关键词路径已经回答了问题，此时进行生成调用只会对一个已经定位好的数值进行格式化。

#### 2.2 A question that needs the model
#### 2.2 需要模型的问题

Now ask “which guarantees can I avoid in my case?” against the same policy. The keyword scorer runs the same way, but the result is different in kind. Three lines tie at a score of 2: the two optional guarantees and the line that mentions adjusting them. The margin between first and second is zero. No single line stands out, because the question is not asking for a line.
现在，针对同一份保单询问“在我的情况下，我可以避免哪些担保？”。关键词评分器的运行方式相同，但结果性质完全不同。有三行并列得分为 2：两个可选担保以及提到调整它们的行。第一名和第二名之间的差距为零。没有哪一行脱颖而出，因为这个问题并不是在寻找某一行内容。

“In my case” asks the model to weigh the user’s situation against several optional guarantees and reason about which ones are safe to drop. That is generation work, and the flat score is the tell: the keyword path found candidates, not an answer. One clear winner routes past.
“在我的情况下”要求模型权衡用户的处境与几个可选担保，并推理出哪些是可以安全放弃的。这是生成式工作，而平坦的分数就是信号：关键词路径只找到了候选内容，而非答案。只有一个明确的赢家才能绕过模型。
