# LangChain vs LangGraph: 4 Key Differences and When to Use Each
# LangChain 与 LangGraph：4 个关键区别及选型指南

Agentic AI LangChain vs LangGraph: 4 Key Differences and When to Use Each. A practical guide to choose the proper tool for your agentic workflows and systems.
代理式 AI LangChain 与 LangGraph：4 个关键区别及选型指南。这是一份帮助你为代理工作流和系统选择合适工具的实用指南。

LangChain came to our lives long before LangGraph. This is a clear indication of LangGraph closing a gap. In other words, LangGraph does things that are more complicated or not possible to do with LangChain. In this article, we’ll go over 4 key differences between LangChain and LangGraph, and how they impact the code we write to build agentic workflows. Let’s first mention that these are not competing tools. LangGraph is part of the LangChain ecosystem. It is kind of an extension built on top of LangChain.
LangChain 进入我们的视野远早于 LangGraph。这清楚地表明 LangGraph 旨在填补某些空白。换句话说，LangGraph 能处理那些在 LangChain 中难以实现或无法完成的任务。在本文中，我们将探讨 LangChain 和 LangGraph 之间的 4 个关键区别，以及它们如何影响我们构建代理工作流的代码编写。首先需要说明的是，它们并非竞争关系。LangGraph 是 LangChain 生态系统的一部分，可以看作是构建在 LangChain 之上的扩展。

### 1. Pipeline vs Loops
### 1. 流水线 (Pipeline) 与循环 (Loops)

LangChain is a pipeline with a clear direction: We chain components together but in one direction, which looks like this in code: `chain = prompt | model | parser` -> `output = chain.invoke(input)`. We can still branch, run steps in parallel, and construct DAGs, but the default abstraction is data being moved forward through a pipeline. This structure is enough for solving many problems such as: Retrieve documents, then generate an answer; Extract fields, then save them; Summarize text, then classify it. However, when it comes to sending backward, we need to write an outer Python loop. Hence, the application handles the rest, not LangChain.
LangChain 是一个具有明确方向的流水线：我们将组件串联在一起，但方向是单向的，代码表现为：`chain = prompt | model | parser` -> `output = chain.invoke(input)`。虽然我们仍然可以进行分支、并行运行步骤并构建有向无环图 (DAG)，但其默认抽象是将数据通过流水线向前推进。这种结构足以解决许多问题，例如：检索文档后生成答案；提取字段后进行保存；总结文本后进行分类。然而，当涉及到向后回溯时，我们需要编写外部的 Python 循环。因此，其余部分由应用程序处理，而非 LangChain。

On the other hand, LangGraph treats loops as part of the workflow itself. It is basically a graph with nodes and edges. A node performs a particular task. A normal edge defines fixed transitions between nodes. A conditional edge decides where to go next. Thanks to the normal and conditional edges, we can route back to earlier nodes without a hustle.
另一方面，LangGraph 将循环视为工作流本身的一部分。它本质上是一个由节点和边组成的图。节点执行特定任务，普通边定义节点之间的固定转换，条件边决定下一步的走向。得益于这些普通边和条件边，我们可以轻松地回溯到之前的节点。

### 2. Stateless vs Stateful
### 2. 无状态 (Stateless) 与有状态 (Stateful)

A LangChain pipeline does not hold a state within itself. Each runnable usually receives an input and returns an output. State is passed forward in the form of a dictionary, message, or a custom object. This is enough when each step needs only the previous step’s result. However, once we have a more complex workflow with loops or branches, it is on us to track the current draft, validation errors, conversation history, retry counts, etc. We can manage all of that writing extra Python code but, as we mentioned earlier, it’s not part of the chain.
LangChain 流水线本身不持有状态。每个可运行单元通常接收输入并返回输出。状态以字典、消息或自定义对象的形式向前传递。当每个步骤仅需前一步的结果时，这已经足够。然而，一旦我们有了包含循环或分支的复杂工作流，我们就必须自行跟踪当前草稿、验证错误、对话历史、重试次数等。我们可以通过编写额外的 Python 代码来管理这一切，但正如前面提到的，这并不属于链本身。

LangGraph creates stateful agents so the state is part of the graph. We declare a schema for the state, usually in the form of a `TypedDict`. A node does not have to reconstruct the entire state. It can do partial updates and LangGraph handles it smoothly. LangGraph then merges that update into the existing state. State fields can also have reducers for values written by multiple nodes or same node multiple times.
LangGraph 创建有状态的代理，因此状态是图的一部分。我们通常以 `TypedDict` 的形式为状态声明模式。节点无需重构整个状态，它可以进行部分更新，而 LangGraph 会平滑地处理这些更新，并将其合并到现有状态中。状态字段还可以为由多个节点或同一节点多次写入的值设置“归约器”(reducers)。

### 3. Human-breaks-the-loop vs Human-in-the-loop
### 3. 人工中断循环 (Human-breaks-the-loop) 与 人机协同 (Human-in-the-loop)

We’ve witnessed agents making crucial mistakes. So, especially for some critical tasks, we may want to intervene with agents operations. Suppose an agent prepares a database migration, refund, or production deployment. We may want a human-in-the-loop to approve it before agent actually executes. With a conventional LangChain pipeline, the common approach is to build that pause into the application surrounding the pipeline. This approach works but requires a lot of work. It sounds more like a human-breaks-the-loop and reconstructs it.
我们已经见证过代理犯下严重错误。因此，特别是在某些关键任务中，我们可能希望干预代理的操作。假设代理准备执行数据库迁移、退款或生产环境部署，我们可能希望在代理实际执行前通过“人机协同”进行审批。在传统的 LangChain 流水线中，常见的做法是将这种暂停构建在流水线周围的应用程序中。这种方法可行，但需要大量工作，听起来更像是“人工中断循环”并重新构建它。

On the other hand, LangGraph provides dynamic `interrupt()` calls inside nodes. Interrupts allow us to pause graph execution at specific points and wait for external input to continue. When we trigger an interrupt, LangGraph saves the graph state so we don’t need to worry about losing information or data.
另一方面，LangGraph 在节点内部提供了动态的 `interrupt()` 调用。中断允许我们在特定点暂停图的执行，并等待外部输入以继续。当我们触发中断时，LangGraph 会保存图的状态，因此我们无需担心信息或数据丢失。

### 4. Restarts vs Resume
### 4. 重启 (Restarts) 与 恢复 (Resume)

When a step in a normal chain fails, the simplest way to recover is often to invoke the chain again. This can be an expensive option because preceding model calls, retrieval queries, transformations, other tool calls need to be repeated. We can add caching and write custom resume logic but those would not be part of the chain. Similar to our discussing in previous points, these are handled on the application level, not in LangChain.
当普通链中的某个步骤失败时，最简单的恢复方法通常是再次调用该链。这可能是一个昂贵的选择，因为之前的模型调用、检索查询、转换和其他工具调用都需要重复执行。我们可以添加缓存并编写自定义的恢复逻辑，但这些都不属于链的一部分。与我们之前讨论的几点类似，这些是在应用程序层面处理的，而不是在 LangChain 中。

LangGraph has something called `checkpointer`, which is a state persistence layer that saves a snapshot of an agent’s graph state at every step of execution.
LangGraph 拥有名为 `checkpointer` 的功能，这是一个状态持久化层，可以在执行的每一步保存代理图状态的快照。
